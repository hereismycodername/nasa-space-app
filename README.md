# Space Health — Rust + React

Локальный стенд NASA Space Apps: симулятор → Rust/Axum → SQLite;
React, оконный egui и терминальный ratatui используют один HTTP API.
Интернет во время работы не нужен; браузеру нужен доступ к локальному серверу.
Зарегистрированные устройства могут отправлять измерения по HTTP; для USB/UART
есть шлюз с очередью подтверждения. Запуск на физической плате и клиническая
точность пока не подтверждены. Инструкции: [датчики и Raspberry Pi](docs/hardware.md).

Исходное [описание проекта и задачи хакатона](docs/project-brief.md).

## AstroCheck: интерфейс Crew / Ground

Оформление и анатомическая схема из ветки `ui` перенесены в основной React-клиент.
Дизайн обновлён по `ui@b24fa01`: прямые углы, срезы на панелях, квадратные
маркеры, сегментные шкалы и фокус на выбранной системе организма. Шкалы показывают
полноту измерений, а не демонстрационный индекс здоровья из native-интерфейса.
Crew показывает обзор, Ground — консоль того же демо-астронавта: дерево показателей,
несколько графиков с общей шкалой UTC, текущие наблюдения и выбранный профиль.
Переключатель меняет представление, а не права доступа. В левой панели доступны
органы, скелет и рентген; выбор системы фильтрует показатели.

Карта тела теперь содержит объёмные поверхности BodyParts3D. Тяните модель мышью
или одним пальцем, чтобы повернуть её; колесо мыши или жест двумя пальцами меняют
масштаб. Стрелки клавиатуры вращают модель, `+`/`−` меняют масштаб, `Home` и кнопка
«Исходный ракурс» возвращают вид спереди. Орган можно выбрать прямо на модели
или кнопкой под ней. В Ground выбор добавляет связанные показатели на графики.
Переключатель `2D` сохраняет прежнюю карту; при ошибке загрузки или недоступном
WebGL она показывается автоматически. 3D требует WebGL 2 в браузере клиента;
на физической Raspberry Pi производительность пока не измерена.

Все двенадцать метрик читаются из общего API с сохранённой семантикой BE-06. Вкладка «Динамика» поддерживает
24 часа, 7 и 30 дней; сохраняет пробелы и происхождение времени. «Внести измерение»
сохраняет выбранный показатель с известным или неизвестным временем. Черновик и
ключ повтора сохраняются при переходах между разделами. Успех формы и отметки
задач показывается после ответа сервера; задачи пока не сбрасываются автоматически.

Кольцо показывает полноту данных, не медицинский балл. Текущие наблюдения Ground
отражают quality из того же ответа latest; это не постоянный журнал событий.
Демонстрационные нормы,
baseline, XP, четыре вымышленных члена экипажа и отправка сообщений из native UI
не подставляются в реальные данные. Эти возможности требуют последующих этапов backend.

Для экономии ресурсов обзор загружается одним циклом параллельных запросов каждые
5 секунд без перекрытий; скрытая вкладка отменяет опрос. Графики загружаются отдельным
JS-модулем при открытии динамики или Ground и обновляются раз в 15 секунд.
Ground запрашивает выбранные метрики параллельно с едиными from/to/maxPoints;
скрытая вкладка отменяет запросы. SVG-геометрия BodyParts3D и координаты маркеров
подготовлены заранее из `ui/crates/ui-model/src/anatomy.rs`, без расчёта сплайнов в браузере.
Повторный экспорт: `rustc scripts/export-anatomy.rs -o /tmp/export-anatomy`, затем
`/tmp/export-anatomy > src/features/anatomy/anatomyData.ts`.
3D-геометрия лежит в `public/anatomy/body.glb` и включается в обычную сборку.
Three.js загружается отдельным модулем; кадры рисуются при взаимодействии,
изменении слоя, выделения или размера окна. Постоянного цикла анимации нет.
Модель, шрифты и код обслуживает локальный сервер; внешние CDN не требуются.
Источники и повторная генерация 3D: [BodyParts3D](public/anatomy/README.md).
Происхождение и условия использования: [анатомия](public/anatomy-credits.txt),
[шрифты](public/fonts/).

Оконный egui и терминальный ratatui находятся в отдельном workspace `ui/`.
По умолчанию они подключаются к этому же серверу через общий клиент `ui-http`:
измерения и отметки задач синхронизируются с React. Самостоятельный `DemoBackend`
включается только флагом `--demo`. [Запуск нативных интерфейсов](ui/README.md).

## Три интерфейса с общими данными

Сначала запустите один сервер командой `npm run demo` из корня проекта.
React доступен по `http://127.0.0.1:8080`. В других терминалах из того же корня:

```bash
# Оконное приложение
cargo run --locked --manifest-path ui/Cargo.toml -p ui-gui
# Терминальное приложение (выход: q)
cargo run --locked --manifest-path ui/Cargo.toml -p ui-tui
```

У обоих клиентов есть `--api-url http://<адрес-сервера>:8080` и переменная
`ASTROCHECK_API_URL`; явный аргумент имеет приоритет. Для доступа с другого
компьютера сервер должен слушать LAN-интерфейс (см. раздел запуска на Pi).
`localhost` на втором компьютере означает этот второй компьютер, а не сервер.
Оконная и терминальная версии не открывают свою SQLite и не запускают копию API.
Все три клиента используют профиль `demo-astronaut` и двенадцать показателей.
Реестр из шести показателей тоже поддерживается, но API задач должен иметь
формат BE-07 `{missionDate, tasks}`. Обновляйте сервер и все три клиента вместе;
старый массив задач BE-06 больше не поддерживается.

Нативные клиенты обновляют показания и задачи примерно раз в 2 секунды, а
семидневные графики — раз в 10 секунд. Графики используют UTC-время и сохраняют
пустые интервалы. Источник записи, время измерения/получения и свежесть показаны
отдельно от демонстрационной оценки BE-08. Запись считается
сохранённой только после подтверждения API; при потере связи видны ошибка и
последние полученные данные. Демонстрационные данные автоматически не включаются.
Неподтверждённые отправки не являются постоянной очередью на диске; не закрывайте
клиент, пока он отправляет запись. Мост USB/UART имеет отдельную постоянную очередь.

Сборка исполняемых файлов:

```bash
cargo build --locked --release --manifest-path ui/Cargo.toml -p ui-gui -p ui-tui
```

Обычно файлы находятся в `ui/target/release/`: `astrocheck-gui` и `astrocheck-tui`
(на Windows — с расширением `.exe`). При `CARGO_TARGET_DIR` путь отличается.
Сборка на macOS не создаёт Windows `.exe`: собирайте для целевой ОС.
Офлайн-макеты с отдельными демонстрационными данными запускаются с `--demo`.
Вращаемая 3D-модель остаётся функцией React; оконная версия использует 2D-анатомию.

Сквозная проверка двух независимых нативных клиентов и запросов браузерного
контракта на временном сервере/SQLite: `npm run test:native-api`.

## Оценка и действия BE-08

Во всех трёх интерфейсах состояние данных отделено от результата правил:
«без срабатываний», «внимание», «срочно привлечь помощь» или «не оценено».
Каждый сигнал содержит показатель, причину, следующий шаг, маршрут помощи
и ссылки на источники. Доступны пояснения пяти опасностей космического полёта.
При потере связи, устаревании или смене измерения старый вывод не выдаётся за текущий.

Правила `be08-demo-1` оценивают шесть исходных показателей только по свежим
измерениям с известным временем. Это демонстрационная поддержка самонаблюдения,
не диагноз и не валидированный протокол NASA. Отсутствие срабатываний не означает
здоровье всех органов. Симптомы, требующие срочной помощи, указаны независимо
от чисел; приложение не отправляет сообщения экипажу или врачам автоматически.

Пороги, источники и ограничения: [BE-08](docs/be08-rules.md).
Сквозная проверка с отдельной SQLite: `npm run test:assessment`.
Добавление B/C согласовано в [Issue №6](https://github.com/hereismycodername/nasa-space-app/issues/6#issuecomment-6884532125):
сервер iwbhappy интегрирован, новые данные без правил остаются «не оценено».
B/C добавляет SpO₂, глюкозу, нечёткость зрения, активность за 24 часа, головную боль
и боль в спине. Выбор области тела открывает подходящий ввод; нули и дроби допустимы
в пределах контракта. Эти дополнительные метрики пока не имеют правил оценки.

## Требования

- Node.js из `.nvmrc`, npm.
- Rust 1.100.0, Cargo, rustfmt и clippy (через rustup, версия в `rust-toolchain.toml`).
- Системный C compiler для сборки SQLite: Xcode Command Line Tools на macOS,
  `build-essential` на Debian/Raspberry Pi OS, MSVC Build Tools на Windows
  (для проверки `doctor` используйте Developer PowerShell с `cl.exe` в PATH).
- При первом скачивании зависимостей нужен интернет.

## Быстрый запуск с симулятором

Из корня проекта с установленными Node.js и Rust:

```bash
npm ci
npm run doctor
npm run demo
```

Команда собирает React и Rust, ожидает готовность API и запускает симулятор.
Откройте напечатанный адрес, по умолчанию `http://127.0.0.1:8080`.
Ctrl+C завершает запущенные ею процессы. Если порт занят, команда объясняет причину;
можно задать другой `BIND_ADDR`, например `127.0.0.1:18082`.
Повторный запуск без сборки: `npm run demo -- --no-build`.
Cargo ищется также в стандартном каталоге rustup, даже если его нет в PATH.
`npm run doctor` показывает версии, архитектуру, память и сведения об ОС/плате.

## Разработка — три терминала из корня репозитория

```bash
nvm use
source "$HOME/.cargo/env" # если cargo ещё не доступен в PATH
npm ci
npm run server
```

```bash
npm run dev
```

```bash
npm run simulator
```

UI: http://localhost:5173. Vite проксирует `/api` на `127.0.0.1:8080`.
Rust создаёт `space-health.db` и применяет миграции при запуске.
Симулятор отправляет синтетический пульс каждые 2 секунды. Ctrl+C останавливает
процесс. После остановки симулятора пульс становится stale, когда возраст
последнего известного измерения превысит 15 секунд.
Это демонстрационный порог свежести, не клинический порог.

Для конечного прогона:

```bash
SIM_COUNT=10 npm run simulator
```

Если сервер недоступен, симулятор повторяет отправку того же сообщения.
Одинаковый `(deviceId, sessionId, sequence)` не создаёт дубликат.
Новая сессия генерируется при каждом запуске симулятора.

## Живая демонстрация для питча

```bash
npm run pitch
```

Команда собирает приложение и запускает отдельный стенд на
`http://127.0.0.1:8082` с временной SQLite. Показания попадают в настоящий API;
рабочая БД и обычный симулятор не используются. После остановки временная БД
удаляется. Для повторного выступления с готовой сборкой: `npm run pitch -- --no-build`.

По умолчанию пять сцен сменяют друг друга каждые 30 секунд и повторяются по кругу.
Пульс, давление, температура, SpO₂ и глюкоза обновляются каждые две секунды;
React забирает новые данные примерно каждые пять секунд. Сон, самочувствие,
симптомы и активность меняются при входе в сцену: это ускоренная демонстрация
самоотчётов, а не показания физических датчиков. Все записи имеют источник `simulator`
и настоящее время отправляемого измерения; часы сервера не перематываются.

| Сцена / клавиша | Что показать аудитории |
|---|---|
| `baseline` / `1` | Значения поступают, карточки обновляются; исходные шесть правил не срабатывают |
| `attention` / `2` | Показания меняются, появляются предупреждения с объяснением и следующим действием |
| `critical` / `3` | Срочный сигнал по давлению и подсказка о привлечении экипажа |
| `recovery` / `4` | Новые показания снимают прежние срабатывания; это сценарий восстановления, не доказательство лечения |
| `stale` / `5` | Отправка прекращается, сервер продолжает работать; спустя 15 секунд пульс теряет свежесть |

У новых шести метрик B/C пока нет правил: они остаются «Не оценено» даже при свежих
значениях. Поэтому `baseline` не обещает общую зелёную оценку всех 12 показателей.
На питче удобно показывать живые карточки и объяснения; семидневный масштаб графиков
агрегирует короткое выступление в несколько точек.

Управление — в терминале запуска: `1`–`5` выбирают сцену, `n` переходит к следующей,
`r` начинает сценарий заново. Пробел или `p` останавливает только автоматическую
смену сцен: текущие показания продолжают поступать. `q` или Ctrl+C завершает стенд.
В обычном интерактивном терминале клавиши работают сразу. При передаче команд
через pipe используйте одну команду на строку; `shutdown` также завершает процесс.

```bash
# Ведущий сам переключает сцены
npm run pitch -- --manual

# Один проход, сцены по 45 секунд, другой порт
npm run pitch -- --cycles 1 --stage-seconds 45 --port 8083

# Отправлять в уже работающий API: записи попадут в его базу
npm run pitch -- --api-url http://127.0.0.1:8080

# Только источник показаний, без запуска сервера и сборки
npm run pitch:sensors -- --api-url http://127.0.0.1:8080 --cycles 1
```

`--interval-ms` задаёт интервал отправки в миллисекундах. Сцена должна длиться
не меньше двух интервалов; `stale` в автоматическом режиме длится минимум 30 секунд,
чтобы было видно потерю свежести. Перед началом проверяется
поддержка всех 12 метрик; сообщения при сетевой ошибке повторяются с тем же ключом
и не создают дубликаты. Не запускайте второй генератор против того же API во время
питча: его новые значения будут смешиваться со сценарием.

Для одновременного показа оконной и терминальной версий подключите их к стенду:

```bash
cargo run --manifest-path ui/Cargo.toml -p ui-gui -- --api-url http://127.0.0.1:8082
cargo run --manifest-path ui/Cargo.toml -p ui-tui -- --api-url http://127.0.0.1:8082
```

Все три интерфейса читают одни записи; 3D-модель остаётся только в браузере.

Проверка симулятора и запуска: `npm run test:tooling`. Покрыты сцены, точные повторы
после потери ответа, задержки сети, ручное управление, изоляция БД и остановка.
На macOS дополнительно проверены полный автоматический цикл и ручной прогон
с настоящим Rust API/React: срабатывания, восстановление и естественное устаревание.
Стенд питча по умолчанию отключает журнал каждого HTTP-запроса, чтобы не скрывать
управление сценами. Для диагностики можно задать `REQUEST_LOG=1`.

## Демо-сценарии

Сценарий показа и чек-лист демо-машины: [docs/demo-runbook.md](docs/demo-runbook.md). Текст питча: [docs/pitch.md](docs/pitch.md).

Все четыре сценария включают spo2, glucose, visionBlur, exerciseMinutes, headache и backPain; attention меняет их синтетические профили за последние трое суток.
Live по умолчанию отправляет только пульс; свежесть последнего spo2 истекает через
2 часа от времени измерения. В питч-симуляторе spo2 обновляется вместе с другими
показаниями приборов.

`npm run demo` — быстрый стенд с живым симулятором; `demo:prepare` / `demo:start` —
воспроизводимые семидневные сценарии в отдельных БД.

Все показания синтетические; устройство `simulator-01`, источник в API — `simulator`.
Нужны Node 24 и Rust. Команды одинаковы для PowerShell и Linux, запускаются из корня:

```text
npm run build
npm run demo:prepare -- --scenario baseline --seed 42 --reference 2026-11-14T12:00:00Z
npm run demo:start -- --scenario baseline --port 8080
```

Если обычное демо уже работает на 8080, используйте для сценария `--port 8081`.
Занятый порт вызывает ошибку запуска; сценарий не использует чужой сервер.
GUI и TUI подключаются к данным выбранного сценария через
`--api-url http://127.0.0.1:8081`; браузер открывает этот же адрес.

Старые подготовленные БД сохраняют исходные данные. Чтобы получить историю новых
шести метрик B/C, остановите выбранный сценарий и повторите `demo:prepare` с
`--force`: это пересоздаёт только его `demo/<scenario>.db`. Рабочая БД не меняется.
Повтор пакетов старой версии генератора не заменяет подготовку новой истории.

| Сценарий | Что показывает |
|---|---|
| `baseline` | Семь суток: пульс каждые 5 минут с суточным ритмом и двумя короткими нагрузками днём; давление дважды (07:30 и 19:30 UTC), температура трижды, сон утром, mood вечером |
| `attention` | Последние 3 суток: сон 4–5 ч, пульс покоя +12–15 bpm, систолическое давление +10–14 mmHg, диастолическое +6–9 mmHg, mood 2. Данные для демонстрационных правил BE-08; устаревшие показатели не оцениваются |
| `stale` | Потоки обрываются минимум за 6 ч до reference, сон — минимум за 2 суток; живой симулятор не запускается |
| `delayed` | Последние 30 минут пульса отправляются буфером со старыми measuredAt в детерминированно перемешанном порядке; три прежних сообщения повторяются с теми же ключами |

Давление хранится парой отдельных показаний с одинаковым measuredAt: обычно
систолическое около 110–125 mmHg, диастолическое 68–80 mmHg, вечером немного выше.
Разница всегда не меньше 25 mmHg. Это только синтетическая история: в attention
давление повышено последние три суток; stale/delayed применяют к нему общее отсечение.

`prepare` создаёт только `demo/<scenario>.db` через настоящий HTTP API. Сервер всегда
проверяется через `cargo build --locked`; Cargo пересобирает изменившийся код.
Рабочая `space-health.db` не используется.
Итоговая сводка показывает число HTTP 201, 200 и ошибок по метрикам; ошибка прерывает
подготовку с ненулевым кодом. Для восстановления (также после прерванной подготовки):

```text
npm run demo:prepare -- --scenario baseline --seed 42 --reference 2026-11-14T12:00:00Z --force
```

Без `--force` существующая БД вызывает ошибку. `--force` удаляет только
`demo/<scenario>.db*`, включая служебные SQLite-файлы и метаданные `.db.json`.
Перед восстановлением остановите запущенный стенд Ctrl+C.
Другие пути и произвольные имена сценариев не поддерживаются.

Seed по умолчанию — `42`, reference — текущее время UTC до начала минуты.
Оба параметра печатаются и сохраняются в `demo/<scenario>.db.json`. Чтобы воспроизвести
показания точно, используйте напечатанные seed/reference с тем же сценарием.
История покрывает `[reference − 7 суток, reference)`; расписание суток задано в UTC.
Reference должен позволять отправку через API: будущие относительно сервера измерения
более чем на 5 минут контракт отклоняет. Повторная отправка массива из
`generateHistory({ scenario, seed, reference })` на эту БД возвращает только 200;
ключ сообщения — `(deviceId, sessionId, sequence)`. Не смешивайте разные reference
при одинаковых scenario/seed в одной БД: sessionId не содержит reference.

`start` автоматически выполняет prepare с параметрами по умолчанию, если БД отсутствует;
печатает адреса UI, latest и series за семь суток подготовленной истории.
При отсутствии `dist/` предупреждает о необходимости `npm run build`.
Для baseline/attention/delayed запускается текущий живой симулятор пульса.
Профиль `SIM_PROFILE=attention` продолжает синтетическое смещение пульса +12–15 bpm;
baseline/delayed используют `normal`. Это тестовые данные, не медицинское
заключение о здоровье: оценка BE-08 отдельно учитывает свежесть и ограничения правил.
Он также делает пульс актуальным после показа delayed-буфера. Остальные одиннадцать метрик
остаются историческими. Ctrl+C останавливает оба процесса.

Ограничение MVP: живой симулятор держит в памяти одно неподтверждённое сообщение
и приостанавливает генерацию до его отправки. Постоянной очереди на всё время
разрыва и восстановления очереди после рестарта нет.

## Выпуск и показ

Один release-процесс Rust раздаёт UI и API на `http://127.0.0.1:8080`, без Vite.
`npm run release` собирает `dist`, сервер и `space-health-admin` через
`cargo build --release --locked --bins`,
ожидает API и запускается **без симулятора**. Для живого потока добавьте
`npm run release -- --simulator`. Ctrl+C останавливает дочерние процессы через
stdin на Windows и сигналом группе процессов на Unix; через 10 секунд используется
принудительная остановка.
Сервер заканчивает текущие запросы и печатает `Server stopped gracefully.`.
На Linux прямой запуск и systemd также принимают SIGINT/SIGTERM.

Подготовка и запуск из корня репозитория (PowerShell):

```powershell
$env:PATH = "$env:USERPROFILE\.cargo\bin;$env:PATH" # если Cargo отсутствует в PATH
npm ci
rustup show
npm run release
```

То же в bash:

```bash
source "$HOME/.cargo/env" # если Cargo отсутствует в PATH
npm ci
rustup show
npm run release
```

Если нужен только готовый комплект без запуска, в обеих оболочках:

```text
npm ci
npm run build
cargo build --release --locked --bins
```

В комплект выпуска входят `space-health-server`, `space-health-admin` и весь `dist/`.
В стандартной конфигурации оба бинарника находятся в `target/release/`
(Windows: `.exe`). При изменённом Cargo target лаунчер берёт пути из Cargo artifact:
сервер — в строке `Ready`, admin — в строке `Admin (release)` после сборки.
Для готовой release-сборки без пересборки:
`npm run release -- --no-build`; при переносе можно задать `SERVER_BINARY`.
Обычный `npm run start` по-прежнему запускает последнюю debug-сборку.

Admin CLI не запускает HTTP-сервер. Используйте ту же `DATABASE_URL`, что у сервера.
Из корня проекта перейдите в release-папку, PowerShell:

```powershell
$releaseRoot = (Get-Location).Path
$env:DATABASE_URL = 'sqlite://' + $releaseRoot.Replace('\', '/') + '/space-health.db'
Push-Location .\target\release
& .\space-health-admin.exe --help
& .\space-health-admin.exe register-device sensor-01
& .\space-health-admin.exe list-devices
Pop-Location
```

В bash:

```bash
release_root="$(pwd -P)"
export DATABASE_URL="sqlite://${release_root}/space-health.db"
(
  cd target/release
  ./space-health-admin --help
  ./space-health-admin register-device sensor-01
  ./space-health-admin list-devices
)
```

При запуске admin из самой release-папки или другой директории задайте абсолютный
`DATABASE_URL` по примеру ниже; относительный путь зависит от текущей папки.

### Готовый бинарник из другой папки

По умолчанию пути БД и `dist` разрешаются относительно **текущей папки процесса**.
`.env` автоматически не читается. Задайте абсолютные пути; родительская папка БД
должна существовать и быть доступна для записи. В PowerShell, из корня проекта:

```powershell
$releaseRoot = (Get-Location).Path
$env:DATABASE_URL = 'sqlite://' + ($releaseRoot.Replace('\', '/')) + '/space-health.db'
$env:FRONTEND_DIST = Join-Path $releaseRoot 'dist'
$env:BIND_ADDR = '127.0.0.1:8080'
# Например: sqlite://C:/PROJECTS/NASA2026hackathon/nasa-space-app/space-health.db
Set-Location $env:TEMP
& (Join-Path $releaseRoot 'target/release/space-health-server.exe')
```

В bash, из корня проекта:

```bash
release_root="$(pwd -P)"
export DATABASE_URL="sqlite://${release_root}/space-health.db"
export FRONTEND_DIST="${release_root}/dist"
export BIND_ADDR=127.0.0.1:8080
# Например: sqlite:///opt/space-health/space-health.db
cd /tmp
"${release_root}/target/release/space-health-server"
```

Ctrl+C завершает и прямой запуск. `SHUTDOWN_STDIN=1` нужен только супервизору:
строка или EOF на stdin запрашивает штатную остановку. Лаунчеры задают его сами
на Windows, а на Unix посылают сигналы группе процессов.
Подтверждённые API записи остаются в SQLite после остановки и перезапуска.
Отсутствие `dist/index.html` даёт предупреждение, API продолжает работать.
Неверный URL БД, недоступный каталог и ошибка bind завершают сервер с кодом 1
и подсказкой в stderr. `REQUEST_LOG=0` отключает строки запросов; ошибки остаются
в stderr. Логи `/api/*` содержат метод, путь без query, статус и миллисекунды,
без тел и значений измерений; запросы статики не логируются.

### Локальная сеть

Для запуска лаунчера из корня проекта в PowerShell:

```powershell
$env:BIND_ADDR = '0.0.0.0:8080'
npm run release
ipconfig # выполнить в другом терминале; нужен IPv4 активного Wi-Fi/Ethernet
```

В bash:

```bash
BIND_ADDR=0.0.0.0:8080 npm run release
hostname -I # выполнить в другом терминале; выбрать адрес локальной сети
```

Для прямого бинарника замените `BIND_ADDR` в примерах выше на `0.0.0.0:8080`.
Откройте `http://<LAN-IP компьютера>:8080` с этой машины и второго устройства
в той же сети. В Windows при необходимости вручную разрешите входящий TCP 8080
для профиля **Частная сеть** в «Брандмауэр Защитника Windows → Дополнительные
параметры → Правила для входящих подключений». Скрипты брандмауэр не меняют.

**Без авторизации и TLS — только доверенная сеть и синтетические данные.**
Не публикуйте API в интернет. Второе устройство, правила брандмауэра и изоляцию
Wi-Fi нужно проверить на месте; успешный запрос по собственному LAN-IP этого
не заменяет.

### Восстановление и работа без интернета

Остановите стенд Ctrl+C, затем из корня проекта восстановите только demo-БД:

```text
npm run demo:prepare -- --scenario baseline --force
```

Для release-показа подготовленной истории задайте `DATABASE_URL` на
`sqlite://demo/baseline.db` (из корня) или абсолютный путь к ней и выполните
`npm run release -- --no-build`. `demo:start` остаётся отдельным debug-стендом
со сценарием и живым потоком. Для точного воспроизведения используйте сохранённые
seed/reference из `demo/baseline.db.json`. Рабочую `space-health.db` сброс не меняет.

Заранее, с интернетом, выполните `npm ci`, сборку и при необходимости
`demo:prepare`. Возьмите оба release-бинарника для совместимой ОС/архитектуры.
Готовому серверу нужны `dist/` со всеми assets и доступная
SQLite на совместимой ОС/архитектуре; Node, Cargo и интернет для его работы не нужны.
Переносите весь `dist/`, а не один `index.html`. Шрифты и ресурсы UI локальные.
Для переноса существующей БД сначала штатно остановите сервер; не копируйте один
`.db` во время записи с активным WAL. Первый запуск создаёт новую БД автоматически.
Сборка или восстановление истории без сети требуют уже подготовленных зависимостей;
готовый прямой бинарник ничего не скачивает. Сохраните LAN при проверке offline.

Перед показом:

- Проверить Node по `.nvmrc`, `rustup show`, `npm ci` и `npm run doctor` на машине сборки.
- Собрать release и весь `dist/`, подготовить нужный сценарий с seed/reference.
- Проверить напечатанные абсолютные пути БД, статики и путь release-бинарника.
- Открыть UI, `/api/health` и семидневный график без Vite.
- Сохранить измерение, остановить Ctrl+C, увидеть штатное завершение и запись после рестарта.
- Проверить UI со второго устройства по LAN-IP и доступность порта 8080.
- Отключить внешний интернет, сохранив LAN, и повторить основной сценарий.
- Держать копию остановленной demo-БД и команду её восстановления.

### Raspberry Pi и датчики

Raspberry Pi: целевая платформа — Linux-компьютер с Raspberry Pi OS, предпочтительно
64-bit. Собирайте Rust на самой Pi либо настройте отдельную кросс-компиляцию.
macOS-бинарник не запустится на Pi. Аппаратный запуск на Pi пока не проверен.
Pico, ESP32 и Arduino выступают источниками измерений. ESP с сетевым стеком
может обращаться к HTTP API; устройство с USB/UART использует шлюз на Pi или
обычном компьютере. Потребуются прошивка/драйвер конкретного датчика и его калибровка.
Готовые команды, формат NDJSON и systemd-пример — в [hardware.md](docs/hardware.md).

## Подключение источника измерений

Сначала зарегистрируйте идентификатор в той же БД, которую использует сервер:

```bash
cargo run --locked -p space-health-server --bin space-health-admin -- register-device sensor-01
cargo run --locked -p space-health-server --bin space-health-admin -- list-devices
```

Источник и профиль назначает сервер: `source=sensor`, `astronautId=demo-astronaut`.
Затем устройство может отправлять обычный BE-06 payload в `/api/measurements`,
либо передавать строки `{metric,value,unit,measuredAt?}` шлюзу:

```bash
python3 tools/sensor_bridge.py --device-id sensor-01 --port /dev/ttyACM0
```

USB-режим требует pyserial; установка в venv описана в hardware.md. Без `--port`
шлюз читает stdin. Неподтверждённая запись сохраняется в SQLite outbox и повторяется
с тем же ключом даже после перезапуска. Время измерения без часов на устройстве
остаётся неизвестным; шлюз не подменяет его временем получения.

Если открывали предыдущую PWA-сборку, удалите её service worker в DevTools →
Application → Service Workers → Unregister и перезагрузите страницу.

## Настройки

`.env.example` — справочник. Автоматического чтения `.env` сейчас нет;
переменные передаются через окружение команды.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BIND_ADDR` | `127.0.0.1:8080` | Адрес Rust-сервера |
| `DATABASE_URL` | `sqlite://space-health.db` | SQLite-файл |
| `FRONTEND_DIST` | `dist` | Собранный интерфейс |
| `REQUEST_LOG` | включён | `0` отключает строки HTTP-запросов; ошибки остаются в stderr |
| `SHUTDOWN_STDIN` | выключен | `1` — штатная остановка по строке/EOF stdin для лаунчеров |
| `API_URL` | `http://127.0.0.1:8080` | Сервер для симулятора |
| `SIM_INTERVAL_MS` | `2000` | Интервал симулятора, минимум 100 мс |
| `SIM_COUNT` | `0` | Число сообщений; 0 — непрерывно |
| `SIM_PROFILE` | `normal` | Синтетический live-профиль `normal` / `attention` (+12–15 bpm); синтетические данные, а не медицинский вывод |
| `SIM_RETRY_MS` | `SIM_INTERVAL_MS` | Пауза между повторами одного пакета, минимум 100 мс |
| `SIM_REQUEST_TIMEOUT_MS` | `5000` | Таймаут запроса, 100…60000 мс |
| `SERVER_BINARY` | Путь последней сборки Cargo | Готовый бинарник для `npm run start` / `--no-build` |

BE-01 разделяет сервер на `api/`, `domain/` и `storage/`. BE-02 добавляет
числовое UTC-время, явный `timeBasis` и схему ежедневных задач.
BE-03 сравнивает повторы по нормализованному моменту времени и сохраняет измерения
в транзакции; одновременные повторы используют одну исходную запись.
BE-04 добавляет последние значения всех метрик и историю с фильтрами и страницами.
BE-05 добавляет ряды для графиков по всему диапазону с ограниченным числом точек.
BE-06 рассчитывает свежесть отдельно для каждой метрики и последней доставки.
[Архитектура и интерфейсы модулей](docs/backend-architecture.md),
[OpenAPI 3.1](docs/openapi.yaml), [JSON-примеры](docs/examples/README.md).
Ошибки API используют Problem Details с `code`, `message`, необязательным `field`
и совместимым полем `error`. В v0.2.0 добавлено поле `timeBasis`, изменён порядок
истории на время измерения с явным fallback и введён `unknown-time` для оценки
записи без известного времени. Сервер и React-клиент
нужно обновлять вместе при переходе с v0.1. Контракт v0.3.0 сохраняет payload,
но эквивалентный повтор с другим offset теперь возвращает 200 вместо 409.
Первоначальные `id`, `receivedAt` и написание `measuredAt` сохраняются.
В v0.4.0 GET истории возвращает `{items, hasMore, nextCursor}` вместо массива;
обзор получает данные из `/api/measurements/latest`. Сервер и React-клиент нужно
обновить вместе. Query-фильтры истории теперь действуют, неизвестные параметры
отклоняются.
В v0.5.0 добавлен `/api/measurements/series`: обязательные metric/from/to,
maxPoints от 1 до 500 (по умолчанию 200). Для пульса, давления и температуры
возвращаются mean/min/max/count, для сна и самочувствия — последнее значение
интервала. Пустые интервалы содержат null, происхождение времени явно указано.
Форматы остальных ресурсов сохранены; новая миграция не нужна.
В v0.6.0 latest и assessments дополнены `evaluatedAt`, `quality` и
`latestReceivedQuality`. Для пульса окно 15 секунд, давления/температуры — час,
сна/самочувствия — сутки. Будущее время даёт `clockSkew`, неизвестное —
`unknownTime`; окна демонстрационные. Сводка `status/explanation` оценки
сохранена как deprecated для одной последней принятой записи; карточки используют
качество из своего latest-ответа. Строгие схемы клиента нужно обновить, включая
новый legacy status `clock-skew`; `/assessments` отклоняет query. Миграция не нужна.
BE-07 подключает задачи по дате миссии: `GET /api/tasks` возвращает
`{missionDate, tasks}`, PATCH требует `missionDate`. Повторное выполнение
сохраняет исходное время отметки; новый день имеет собственные выполнения.
После demo-polish окна свежести увеличены для периодических замеров:
SpO₂ — 2 часа, давления/температура/боль — 13 часов, ежедневные показатели —
26 часов. Пульс сохраняет окно 15 секунд. Текущие сроки приходят из API.

Новая миграция `0002` применяется при запуске как к пустой, так и к существующей
БД; `0001` и исходные измерения сохранены. Старые отметки задач переносятся на
UTC-дату `completedAt`, не на день запуска. Невосстановимые отметки сохраняются
для разбора; ограничения описаны в [архитектуре](docs/backend-architecture.md).
Миграция `0003` добавляет индексы для фильтров и latest без изменения данных.

Работает приём измерений, проверка структуры/единиц, дедупликация, хранение,
опрос истории, графики, форма ручного ввода, статус свежести и отметки задач.
История фильтруется по metric и диапазону `[from,to)` и отдаёт страницы по 100
записей по умолчанию (максимум 500) с hasMore/nextCursor. Если время измерения
неизвестно, используется время приёма с `timeBasis=receivedAt`. Обзор читает
независимые последние значения всех двенадцати метрик; неизвестное время последней
доставки показывается отдельно от последнего известного измерения. Сейчас один
демонстрационный астронавт. Шаблоны и выполнения по датам хранятся в БД;
API и все три интерфейса используют дату миссии UTC и отдельные отметки для
каждого дня. Произвольный выбор дня доступен через API; интерфейсы показывают
текущий день миссии.
Графики всех метрик запрашивают выбранный период: 24 часа (96 UTC-интервалов),
7 или 30 дней (до 168 интервалов), охватывая все подходящие измерения
без лимита сырых записей. Пустые интервалы разрывают линию;
неизвестное время измерения учитывается с явным timeBasis.

BE-07 с ежедневными задачами по дате миссии подключён к общему API и клиентам.
Правила BE-08 с источниками подключены отдельно от свежести. Дальше — расширение
правил для метрик B/C, прошивка/драйвер выбранного датчика и аппаратное испытание на Pi.
Клиническая точность правил и индивидуальные ограничения экипажа требуют проверки.

## Проверено в этом окружении

- Frontend: lint, 80 тестов клиента, опроса, обзора, графика, ввода и задач,
  TypeScript и production build. Проверяется отмена/возобновление опроса, сохранение
  ключа повторной отправки, ожидание подтверждения записи, гонка PATCH с обновлением данных
  и привязка подсказки к актуальной точке графика.
- Rust: rustfmt, Clippy без предупреждений, 106 тестов: 36 модульных,
  19 общих API, 8 истории/latest, 13 приёма измерений, 6 миграционных, 9 series,
  9 quality API и 6 admin CLI.
  Проверяются пустая и заполненная БД, UTC-сортировка, перенос задач,
  нормализованные и конкурентные повторы, откат при ошибке без потери исходных данных,
  672 записи за семь дней, среднее/last, пробелы, происхождение времени и границы series.
  BE-06 проверяет независимость метрик, границы TTL и будущего времени с точностью
  до наносекунды, неизвестное время, поздние пакеты и повреждённые timestamps.
- OpenAPI: Redocly без ошибок; все 25 JSON-примеров соответствуют схеме;
  дополнительно проверены выбор измерений, окна и возраст в примерах качества.
  Prism mock проверен запросами /api/health, /api/measurements/latest и /api/assessments;
  ответы прошли проверку по схеме. Реальные latest и assessments проверены на
  пустой БД и смешанных состояниях, включая clockSkew и неизвестную последнюю
  доставку при сохранённом известном измерении. Ранее ответы series проверены на пустом
  диапазоне и mixed-потоке с пробелами. Лицензия проекта пока не определена,
  поэтому Redocly выводит предупреждение info-license.
- Сквозной прогон: симулятор → API → SQLite, выдача UI, проверка series и quality,
  сохранение истории и того же агрегированного ряда после перезапуска сервера.
- Базовый стенд ранее проверен в браузере: подключение к API, появление синтетического пульса и графика,
  успешная ручная тестовая запись.
- BE-04 проверен через Playwright на desktop и mobile: шесть карточек, известное
  и неизвестное время сна показаны отдельно, график содержит только пульс;
  горизонтального переполнения и JS-исключений нет.
- BE-05 проверен через Playwright на реальном API: пустой семидневный график,
  отдельные точки и разрывы, полный UTC-период, ручной ввод и mixed-time tooltip.
  Desktop и mobile 390 px проходят без переполнения, включая открытую подсказку;
  в финальной браузерной проверке ошибок и предупреждений консоли нет.
- Перенос AstroCheck проверен на реальном API: Crew/Ground, три слоя анатомии,
  фильтры мышью и клавиатурой, шесть метрик, unknown-time, POST формы и PATCH задач,
  сохранение черновика при навигации, все периоды графика, offline/reconnect.
  На desktop и mobile 390/320 px нет горизонтального переполнения.
  Графики загружаются отдельно от основного интерфейса при открытии Ground или динамики.
- После интеграции команды Ground также загружает графики отдельно от основного UI;
  синхронный диапазон, отсутствие перекрывающихся запросов и пауза скрытой вкладки
  покрыты тестами. Native workspace собирается отдельно и проходит 22 теста,
  включая исправленные подписи времени и прокрутку выбранных каналов.
- Обновлённый Ground проверен в браузере на desktop и 390/320 px: все шесть
  каналов используют одинаковый UTC-диапазон, выбор и период сохраняются при
  переходах, работают фильтры анатомии, offline/reconnect, ввод и задачи.
  Потерянный ответ POST воспроизведён: повтор отправляет тот же payload и оставляет
  ровно одну запись в SQLite.
- Инструменты: 6 Node-тестов и 7 Python-тестов. Полный `npm run demo` собирает
  React/Rust, подтверждает пакет симулятора и завершает свои процессы. Demo smoke
  проверяет повторный запуск и сохранность истории. Отдельно проверен путь
  admin CLI → bridge → Rust API с source=sensor и неизвестным временем;
  повтор после потери подтверждения и перезапуска не создаёт дубликат.
- На Raspberry Pi и физических датчиках пока не проверено.
- BE-06 проверен через Playwright на реальном API: пять состояний качества,
  свежий пульс рядом с устаревшим сном, отдельная неизвестная/задержанная доставка,
  Crew/Ground, истечение срока между опросами и повтор одного сохранённого ответа.
  При offline свежесть помечается неподтверждённой, после reconnect обновляется.
  Desktop и mobile 390 px без переполнения страницы; таблица имеет собственную прокрутку.
