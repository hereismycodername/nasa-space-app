# API v0.4.0 — реализованный контракт BE-04

Машиночитаемая спецификация: [openapi.yaml](openapi.yaml).
Готовые JSON-запросы и ответы: [examples](examples/README.md).
Границы слоёв и их владельцы: [backend-architecture.md](backend-architecture.md).

BE-04 добавляет последние значения по метрикам и фильтрованную историю.
Series, публичные ежедневные задачи и новые правила остаются в [плане backend](backend-plan.md).

## Общие правила

- Базовый URL: `http://127.0.0.1:8080`; пути начинаются с `/api`.
- JSON — camelCase; успешные ответы — `application/json`.
- Ошибки API — `application/problem+json` с полями `code`, `message` и необязательным `field`.
- JSON body: максимум 2 MiB; POST/PATCH требуют JSON Content-Type.
- Авторизации и rate limiting пока нет. Устройства зарегистрированы в БД,
  но знание deviceId не является аутентификацией. Стенд для синтетических данных
  в доверенной локальной сети.
- Неизвестные поля JSON отклоняются. История принимает только `metric`, `from`, `to`, `limit`;
  неизвестные query-параметры истории возвращают 400 `INVALID_QUERY`.
  `date` пока не выбирает день задач.

## Ресурсы и связи

| Ресурс | Поля/связи |
|---|---|
| Device | В БД связывает deviceId с astronautId и source; API регистрации пока нет |
| Measurement | Принадлежит зарегистрированному устройству; ключ сообщения — deviceId/sessionId/sequence |
| Task | Постоянная запись id/title/completedAt; даты миссии и ежедневного экземпляра пока нет |
| TaskTemplate / TaskCompletion | Внутренние таблицы шаблонов и выполнения по astronautId/taskId/missionDate; публичный API по датам появится в BE-07 |
| Assessment | Вычисляемый результат свежести одной последней принятой записи; в БД не сохраняется |

## Измерения

`POST /measurements` принимает одну запись:

```json
{
  "deviceId": "simulator-01",
  "sessionId": "example-boot-1",
  "sequence": 0,
  "metric": "heartRate",
  "value": 72,
  "unit": "bpm",
  "measuredAt": "2026-11-13T08:00:00Z"
}
```

- `deviceId`, `sessionId`: от 1 до 128 **байт UTF-8**, не символов.
- `sequence`: целое от 0 до 9223372036854775807. Producer увеличивает его на каждое
  сообщение в сессии. Сервер проверяет уникальность, а не порядок поступления.
- `sessionId` меняется при новой сессии устройства; при повторе отправки сохраняется.
- `measuredAt`: RFC3339 с часовым поясом, необязателен; отсутствие и JSON `null`
  означают неизвестное время. Допускается не более пяти минут относительно
  будущего серверного времени. Исходное текстовое представление timestamp сохраняется.
- Неизвестное устройство отклоняется. `astronautId`, `source`, `id`, `receivedAt`, `timeBasis`
  клиент не передаёт; сервер задаёт их сам.

Текущие регистрации: `simulator-01` → `demo-astronaut` / `simulator`,
`manual-01` → `demo-astronaut` / `manual`.

| metric | unit | Граница ввода |
|---|---|---|
| heartRate | bpm | > 0 |
| systolicPressure | mmHg | > 0 |
| diastolicPressure | mmHg | > 0 |
| temperature | °C | > 0 |
| sleepHours | h | 0…24 |
| mood | score | 1…5 |

Все значения конечные; дробное значение допустимо, в том числе для mood.
Границы являются валидацией ввода, а не медицинскими нормами.

Результаты POST:

| HTTP | Результат |
|---|---|
| 201 | Создано измерение; [пример ответа](examples/measurement.response.json) |
| 200 | Эквивалентный повтор: возвращается исходная запись с теми же id, receivedAt и исходным measuredAt |
| 409 | Тот же ключ сообщения, но отличаются metric/value/unit/measuredAt |

При дедупликации `measuredAt` сравнивается как момент UTC: `08:00:00Z` и
`13:00:00+05:00` эквивалентны, как и `.1Z` и `.100Z`. Используется точность
парсера Chrono до наносекунды: учитываются первые девять цифр дробных секунд,
последующие отбрасываются. Различие внутри одной миллисекунды всё ещё даёт 409;
числовые миллисекунды истории не используются для сравнения повторов.
Високосная секунда не приравнивается к следующей обычной секунде.
Отсутствующее поле и `null` — одно неизвестное время, но неизвестное и известное
время считаются разным содержимым. Нормализация нужна только для сравнения:
исходная строка первого сохранённого `measuredAt` не переписывается.
`receivedAt` — серверное UTC-время приёма запроса, создавшего запись, а не время
измерения или завершения транзакции. Повторы не обновляют его.

Одновременные эквивалентные запросы создают одну запись: создавший её запрос
получает 201, остальные — 200 и ту же запись. Если один ключ одновременно
использован для разных payload, побеждает одна запись, а остальные payload
получают 409 и не перезаписывают её. Ошибка операции с БД возвращает 500
`DATABASE_ERROR`; успешный ответ отправляется после подтверждённого сохранения.

`GET /measurements` возвращает `{ "items": [...], "hasMore": boolean }` для `demo-astronaut`,
с сортировкой по эффективному времени UTC по убыванию, затем `id DESC`.
Эффективное время — `measuredAt`, если оно известно, иначе `receivedAt`.
Каждая запись в GET и POST содержит `timeBasis: "measuredAt" | "receivedAt"`,
явно обозначающий выбранное поле. При неизвестном времени `measuredAt` остаётся
`null`; получение сообщения сейчас не подтверждает свежесть измерения.

Сравнение выполняется по целым миллисекундам Unix UTC в SQLite, а не по
RFC3339-строкам. Один момент с разными offsets получает одинаковое значение;
доли меньше миллисекунды отбрасываются. Исходные строки сохраняются без изменений
для ответа; точность сравнения повторов описана выше. При равных миллисекундах порядок
задаёт `id DESC`. Поэтому поздно полученная старая запись занимает своё место
по времени измерения, а не поднимается в начало истории из-за времени приёма.

Пустая история — `{ "items": [], "hasMore": false }`. Все фильтры необязательные:

- `metric`: одна из шести метрик таблицы выше;
- `from`, `to`: RFC3339 с offset, диапазон `[from, to)` по эффективному времени
  `COALESCE(measured_at_ms, received_at_ms)` в целых миллисекундах UTC;
- `limit`: целое 1…500, по умолчанию 100.

Неверная метрика, формат времени или limit возвращают 400 `VALIDATION_ERROR` с `field`.
Если `from >= to` после перевода в миллисекунды, `field` равен `to`.
`hasMore` означает наличие ещё записей с теми же фильтрами: сервер выбирает `limit + 1`,
возвращает первые `limit`. Курсорной пагинации нет. Знак `+` offset в URL кодируется как `%2B`.

`GET /measurements/latest` возвращает `{ "metrics": [...] }`: всегда шесть элементов
в порядке `heartRate, systolicPressure, diastolicPressure, temperature, sleepHours, mood`.
Каждый элемент содержит `metric`, `unit`, `latestKnownMeasurement`, `latestUnknownTimeMeasurement`.
Последнее известное измерение выбирается по `measured_at_ms DESC, id DESC` среди записей
с известным `measuredAt`. Время приёма на этот выбор не влияет.
Отдельное неизвестное время возвращается только если последняя принятая запись метрики
по `received_at_ms DESC, id DESC` имеет `measuredAt: null`.
Поля содержат полный Measurement или `null`; метрики без данных сохраняются с обоими `null`.
Оба endpoint ограничены `demo-astronaut`. Свежесть и статусы latest не вычисляет (BE-06).

## Свежесть

`GET /assessments` возвращает `{status, explanation}`.

| status | Значение в BE-03 |
|---|---|
| no-data | Измерений нет |
| unknown-time | У последней принятой записи нет measuredAt; свежесть установить нельзя |
| stale | Известное measuredAt последней принятой записи старше 15 целых секунд |
| not-evaluated | Данные попадают в текущий порог свежести; медицинские правила не подключены |

Сервер выбирает одну запись по числовому времени приёма UTC по убыванию,
затем `id DESC`. Свежесть рассчитывается только по известному `measuredAt`;
его отсутствие даёт `unknown-time` независимо от времени получения.
Статус пока не вычисляется отдельно по каждой метрике и не означает заключение
о здоровье. Допустимое время в будущем пока не отмечается отдельным `clockSkew`;
это и свежесть каждой метрики относятся к BE-06.

## Задачи

- `GET /tasks`: массив `{id, title, completedAt}`, сортировка по id по возрастанию.
- `PATCH /tasks/{id}`: только `{ "completed": true }` либо false.
- true устанавливает серверное UTC-время; false очищает его до null.
- Повтор true пока меняет completedAt. Идемпотентность по датам — BE-07.
- Неизвестная задача — 404 TASK_NOT_FOUND.
- `date` в JSON пока запрещён; `date` в query не выбирает день.

**Целевая семантика после BE-07:** день миссии в UTC; PATCH адресует конкретный день,
повтор выполнения сохраняет исходное время. Это ещё не контракт работающего API.

В BE-02 добавлена схема шаблонов и выполнения по UTC-дате. Существующий
недатированный API остаётся переходным интерфейсом; выбор дня через него ещё
недоступен. Подробности переноса старых отметок и ограничения миграции описаны
в [архитектуре](backend-architecture.md).

## Health

`GET /health` выполняет запрос к БД и возвращает:

```json
{ "status": "ok", "storage": "sqlite" }
```

Этот ответ подтверждает доступность API и SQLite, а не датчика или актуальность показателей.

## Единый формат ошибок

```json
{
  "type": "urn:space-health:error:validation-error",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invalid unit or value",
  "code": "VALIDATION_ERROR",
  "message": "Invalid unit or value",
  "field": "unit",
  "error": "Invalid unit or value"
}
```

`type` — стабильный URN с кодом в lowercase/kebab-case. `title` — стандартное
название HTTP-статуса. `detail`, `message`, `error` равны; `error` оставлен для
совместимости с прежними клиентами. Новая логика клиента использует `code` и
`field`, а не сравнивает текст. `field` может отсутствовать. Внутренние сообщения
SQLx, пути файлов и stack traces в ответ не включаются.

| HTTP | code | Когда |
|---|---|---|
| 400 | INVALID_JSON | JSON синтаксически неверен |
| 422 | INVALID_BODY | Неверный тип JSON-поля, отсутствующее/неизвестное поле или число вне i64 |
| 415 | UNSUPPORTED_MEDIA_TYPE | Нет подходящего JSON Content-Type |
| 413 | PAYLOAD_TOO_LARGE | Превышен лимит тела запроса |
| 400 | INVALID_QUERY | Не удалось декодировать query в ожидаемую структуру |
| 400 | INVALID_PATH | Некорректный параметр пути |
| 400 | VALIDATION_ERROR | Не выполнены правила метрики, единицы, значения или времени |
| 400 | UNKNOWN_DEVICE | Устройство не зарегистрировано; field=deviceId |
| 409 | SEQUENCE_CONFLICT | Ключ сообщения занят другим содержимым |
| 404 | TASK_NOT_FOUND | Нет задачи с указанным id |
| 404 | NOT_FOUND | Нет указанного API-маршрута |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; заголовок Allow перечисляет допустимые |
| 500 | DATABASE_ERROR | Ошибка операции с БД |
| 400 | INVALID_STORED_TIMESTAMP | Некорректное время в сохранённой записи; сохранён прежний HTTP-статус |

Проверки могут остановиться на первой ошибке. Не полагаться на порядок нескольких
одновременных нарушений. Единый формат распространяется на API, но не на ошибки
раздачи статических файлов вне `/api`.

## Совместимость и развитие

Версия 0.4.0 меняет историю с массива на envelope, добавляет фильтры и `/measurements/latest`.
Сервер и React-клиент обновляются вместе. Пути `/api` сохранены.

В 0.3.0 по сравнению с 0.2.0 изменено сравнение повторов: эквивалентные моменты с разными
offsets возвращают 200 вместо 409. Формы запросов, ответов и ошибок в той ревизии прежние;
изменение не требует новых полей клиента или миграции БД. Клиент не должен
полагаться на побайтовое сравнение `measuredAt` в повторном запросе и ответе.

В 0.2.0 по сравнению с 0.1.1 добавлено поле ответа `timeBasis`, история упорядочивается
по времени измерения с явным fallback, а оценка получила `unknown-time`.
Сервер и встроенный React-клиент обновляются вместе. Клиентам со строгими
схемами нужно добавить поле и вариант статуса; нельзя рассчитывать на прежний
порядок по времени приёма. Формы запросов POST/PATCH и ошибки BE-01 сохранены.
Клиент должен принимать `application/problem+json`, а также уметь показать
обычный текст ошибки от прокси.

Новые маршруты можно добавлять совместимо. Изменение массивов на envelope,
обязательных полей и дат задач требует обновления спецификации, примеров,
контрактных тестов и API-клиента в согласованном выпуске. Публичный период
поддержки/депрекации пока не объявлен: это локальный прототип без внешних клиентов.
