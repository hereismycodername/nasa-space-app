# API v0.8.0 — BE-06 и объяснимая оценка BE-08

Машиночитаемая спецификация: [openapi.yaml](openapi.yaml).
Готовые JSON-запросы и ответы: [examples](examples/README.md).
Границы слоёв и их владельцы: [backend-architecture.md](backend-architecture.md).

Контракт сохраняет BE-06 и добавляет объяснимые демонстрационные правила BE-08.
Публичные ежедневные задачи по датам из [плана backend](backend-plan.md) пока не реализованы.

## Общие правила

- Базовый URL: `http://127.0.0.1:8080`; пути начинаются с `/api`.
- JSON — camelCase; успешные ответы — `application/json`.
- Ошибки API — `application/problem+json` с полями `code`, `message` и необязательным `field`.
- JSON body: максимум 2 MiB; POST/PATCH требуют JSON Content-Type.
- Авторизации и rate limiting пока нет. Устройства зарегистрированы в БД,
  но знание deviceId не является аутентификацией. Стенд для синтетических данных
  в доверенной локальной сети.
- Неизвестные поля JSON отклоняются. История и series принимают только описанные ниже query-параметры;
  неизвестные и повторяющиеся имена отклоняются. `/measurements/latest` и `/assessments` не принимают query.
  `date` пока не выбирает день в публичном API задач.
- История, latest, series и оценка читают данные профиля `demo-astronaut`, выбранного сервером.
  Параметра выбора астронавта нет. Это ограничение демонстрационного стенда, не авторизация.

## Ресурсы и связи

| Ресурс | Поля/связи |
|---|---|
| Device | В БД связывает deviceId с astronautId и source; API регистрации пока нет |
| Measurement | Принадлежит зарегистрированному устройству; ключ сообщения — deviceId/sessionId/sequence |
| HistoryPage | Отфильтрованные items, hasMore и nextCursor для продолжения истории |
| LatestMetric | Три независимые последние записи одной метрики, quality и latestReceivedQuality; null явно означает отсутствие |
| MeasurementQuality | Статус свежести выбранной записи, её measurementId, окно и возраст; вычисляется, в БД не сохраняется |
| MeasurementSeries | Вычисленный ряд одной метрики за весь диапазон; содержит ограниченное число интервалов SeriesPoint |
| SeriesPoint | Агрегат всех измерений внутри UTC-интервала; исходные записи не изменяются |
| Task | Постоянная запись id/title/completedAt; даты миссии и ежедневного экземпляра пока нет |
| TaskTemplate / TaskCompletion | Внутренние таблицы шаблонов и выполнения по astronautId/taskId/missionDate; публичный API по датам появится в BE-07 |
| Assessment | Качество метрик на evaluatedAt, объяснимые правила health и совместимая сводка одной последней принятой записи |

## Измерения

`POST /measurements` принимает одну запись:

```json
{
  "deviceId": "simulator-01",
  "sessionId": "example-boot-1",
  "sequence": 0,
  "metric": "heartRate",
  "value": 72,
  "unit": "bpm",
  "measuredAt": "2026-11-13T08:00:00Z"
}
```

- `deviceId`, `sessionId`: от 1 до 128 **байт UTF-8**, не символов.
- `sequence`: целое от 0 до 9223372036854775807. Producer увеличивает его на каждое
  сообщение в сессии. Сервер проверяет уникальность, а не порядок поступления.
- `sessionId` меняется при новой сессии устройства; при повторе отправки сохраняется.
- `measuredAt`: RFC3339 с часовым поясом, необязателен; отсутствие и JSON `null`
  означают неизвестное время. Допускается не более пяти минут относительно
  будущего серверного времени. Исходное текстовое представление timestamp сохраняется.
- Неизвестное устройство отклоняется. `astronautId`, `source`, `id`, `receivedAt`, `timeBasis`
  клиент не передаёт; сервер задаёт их сам.

Текущие регистрации: `simulator-01` → `demo-astronaut` / `simulator`,
`manual-01` → `demo-astronaut` / `manual`.

| metric | unit | Граница ввода |
|---|---|---|
| heartRate | bpm | > 0 |
| systolicPressure | mmHg | > 0 |
| diastolicPressure | mmHg | > 0 |
| temperature | °C | > 0 |
| sleepHours | h | 0…24 |
| mood | score | 1…5 |

Все значения конечные; дробное значение допустимо, в том числе для mood.
Границы являются валидацией ввода, а не медицинскими нормами.

Результаты POST:

| HTTP | Результат |
|---|---|
| 201 | Создано измерение; [пример ответа](examples/measurement.response.json) |
| 200 | Эквивалентный повтор: возвращается исходная запись с теми же id, receivedAt и исходным measuredAt |
| 409 | Тот же ключ сообщения, но отличаются metric/value/unit/measuredAt |

При дедупликации `measuredAt` сравнивается как момент UTC: `08:00:00Z` и
`13:00:00+05:00` эквивалентны, как и `.1Z` и `.100Z`. Используется точность
парсера Chrono до наносекунды: учитываются первые девять цифр дробных секунд,
последующие отбрасываются. Различие внутри одной миллисекунды всё ещё даёт 409;
числовые миллисекунды истории не используются для сравнения повторов.
Високосная секунда не приравнивается к следующей обычной секунде.
Отсутствующее поле и `null` — одно неизвестное время, но неизвестное и известное
время считаются разным содержимым. Нормализация нужна только для сравнения:
исходная строка первого сохранённого `measuredAt` не переписывается.
`receivedAt` — серверное UTC-время приёма запроса, создавшего запись, а не время
измерения или завершения транзакции. Повторы не обновляют его.

Одновременные эквивалентные запросы создают одну запись: создавший её запрос
получает 201, остальные — 200 и ту же запись. Если один ключ одновременно
использован для разных payload, побеждает одна запись, а остальные payload
получают 409 и не перезаписывают её. Ошибка операции с БД возвращает 500
`DATABASE_ERROR`; успешный ответ отправляется после подтверждённого сохранения.

### История и страницы

`GET /measurements` возвращает `{items, hasMore, nextCursor}`
с сортировкой по эффективному времени UTC по убыванию, затем `id DESC`.
Эффективное время — `measuredAt`, если оно известно, иначе `receivedAt`.
Каждая запись в GET и POST содержит `timeBasis: "measuredAt" | "receivedAt"`,
явно обозначающий выбранное поле. При неизвестном времени `measuredAt` остаётся
`null`; получение сообщения сейчас не подтверждает свежесть измерения.

Сравнение выполняется по целым миллисекундам Unix UTC в SQLite, а не по
RFC3339-строкам. Один момент с разными offsets получает одинаковое значение;
доли меньше миллисекунды отбрасываются. Исходные строки сохраняются без изменений
для ответа; точность сравнения повторов описана выше. При равных миллисекундах порядок
задаёт `id DESC`. Поэтому поздно полученная старая запись занимает своё место
по времени измерения, а не поднимается в начало истории из-за времени приёма.

| Query | Значение |
|---|---|
| metric | Одна из шести метрик; без параметра выбираются все |
| from | Включённая нижняя граница эффективного времени |
| to | Исключённая верхняя граница эффективного времени |
| limit | Целое от 1 до 500, по умолчанию 100 |
| cursor | Непрозрачный nextCursor предыдущей страницы |

Границы — RFC3339 с часовым поясом и точностью до целой миллисекунды. Ненулевая
доля меньше миллисекунды отклоняется; границы не округляются. Диапазон `[from,to)`;
если обе границы заданы, `from` должен быть меньше `to`. Offsets нормализуются в UTC;
в URL знак `+` кодируется как `%2B` (например, через `URLSearchParams`). Фильтры
применяются до лимита. Для неизвестного `measuredAt` диапазон использует `receivedAt`
с сохранением `timeBasis=receivedAt` в каждой записи.

Сервер читает на одну запись больше лимита. `hasMore=true` означает, что ниже текущей
страницы есть ещё подходящие записи; `nextCursor` указывает на пару время/id последней
возвращённой записи. Для продолжения отправить курсор без изменений и сохранить
`metric/from/to`. Курсор не нужно разбирать или строить самостоятельно; входное
значение ограничено 160 байтами UTF-8. На последней
странице `hasMore=false`, `nextCursor=null`; пустой результат —
`{"items":[],"hasMore":false,"nextCursor":null}`. Общий count не вычисляется.

Страницы читают текущую БД и не образуют общего snapshot. Новый пакет с более ранним
временем может появиться на следующей странице; новые записи выше курсора видны
при обновлении первой страницы. Стабильная пара время/id устраняет смещение,
характерное для offset-пагинации, но не обещает неизменный набор между запросами.

Неверные значения metric/from/to/limit/cursor дают 400 `VALIDATION_ERROR` с именем
поля; для неверного порядка границ поле — `to`. Неизвестные и повторяющиеся имена
query-параметров дают 400 `INVALID_QUERY` без `field`.

### Последние значения

`GET /measurements/latest` возвращает `{astronautId, evaluatedAt, metrics}` одним согласованным
снимком чтения. Массив всегда содержит шесть записей в порядке `heartRate`,
`systolicPressure`, `diastolicPressure`, `temperature`, `sleepHours`, `mood`.
У каждой записи есть `metric` и три поля:

| Поле | Как выбирается |
|---|---|
| latestMeasurement | Максимум эффективного UTC-времени, затем id |
| latestKnownMeasurement | Максимум известного measuredAt, затем id; неизвестное время исключается |
| latestReceivedMeasurement | Максимум receivedAt, затем id |

Все поля содержат обычное измерение с `timeBasis` либо `null`. Если по метрике нет
данных, все три поля равны `null`. Поздно доставленный старый пакет не заменяет
более новое известное измерение. Последний пакет без времени отображается отдельно:
он может быть `latestMeasurement`/`latestReceivedMeasurement`, но не скрывает
`latestKnownMeasurement`. Обзор React использует этот ресурс независимо от числа
точек графика: частый пульс не вытесняет сон или самочувствие.

Каждая запись дополнительно содержит `quality` и `latestReceivedQuality`.
Основное качество относится к `latestKnownMeasurement`, а при его отсутствии —
к `latestReceivedMeasurement`. Второе всегда относится к последней доставке.
Идентификатор выбранного измерения возвращается в `measurementId`. Это позволяет
показать свежий известный пульс рядом с предупреждением о новой доставке без времени.
`evaluatedAt` — один серверный UTC-момент для расчёта всего ответа.
Демонстрационные правила BE-08 возвращаются отдельно в `assessments.health`.

### Агрегированные ряды для графиков

`GET /measurements/series` возвращает ряд одной метрики за весь запрошенный
диапазон. Лимит истории в 500 записей здесь не применяется: каждое подходящее
измерение участвует в расчёте. Пагинации у ряда нет; `maxPoints` ограничивает
число возвращённых интервалов, включая пустые.

| Query | Значение |
|---|---|
| metric | Обязательно: одна из шести метрик |
| from | Обязательно: включённая нижняя граница эффективного времени |
| to | Обязательно: исключённая верхняя граница, строго больше from |
| maxPoints | Целое от 1 до 500, по умолчанию 200 |

Границы — RFC3339 с часовым поясом, выровненные по миллисекундам. Все цифры
дробных секунд после третьей должны быть нулями; `.100000Z` допустимо,
`.1000000001Z` отклоняется. После нормализации обе границы должны находиться
в UTC-годах `0001…9999`; проверяется и переход года из-за offset. Отдельного
ограничения длительности нет. Знак `+` в URL кодируется `%2B`.

Пусть `spanMs = to - from` в целых миллисекундах. Тогда
`intervalMs = max(1, ceil(spanMs / maxPoints))`,
а число точек — `ceil(spanMs / intervalMs)`, от 1 до `maxPoints`.
Первый интервал начинается точно в `from`, каждый следующий — через `intervalMs`.
Последний заканчивается в `to` и может быть короче. Это интервалы UTC,
привязанные к началу запроса, а не к полуночи или локальному календарю.
При диапазоне 5 ms и `maxPoints=2` получаются интервалы 3 ms и 2 ms.

Эффективное время — известное `measuredAt`, иначе `receivedAt`, с той же
точностью до миллисекунды, что и в истории. Границы каждого интервала —
`[startAt,endAt)`: запись на правой границе входит в следующий интервал,
запись точно в `to` не входит в ряд. Поздно доставленный пакет с известным
временем учитывается по времени измерения. Исходные значения и timestamps
в БД не меняются.

| Метрики | aggregation | value | min / max |
|---|---|---|---|
| heartRate, systolicPressure, diastolicPressure, temperature | mean | Среднее арифметическое всех значений интервала | Минимум и максимум |
| sleepHours, mood | last | Последнее по эффективному UTC-времени в миллисекундах, затем id DESC | Всегда null |

`last` не означает сумму сна за день или усреднение шкалы самочувствия.
Выбор последней строки детерминирован при одинаковом времени. `count` для обоих
режимов — число **всех** подходящих строк интервала, а не только выбранной строки.

Ответ содержит `astronautId`, `metric`, `unit`, `aggregation`, нормализованные
`from`/`to`, `intervalMs`, `timeBasis` всего диапазона и `points` по возрастанию времени.
Каждая точка содержит `startAt`, `endAt`, `value`, `min`, `max`, `count`,
`measuredCount`, `receivedCount`, `timeBasis`. Все timestamps ответа — UTC с
миллисекундами и суффиксом `Z`; единица соответствует метрике.

`measuredCount` — число строк с известным временем, `receivedCount` — с неизвестным;
их сумма равна `count`. `timeBasis` учитывает все строки интервала или всего ряда:
`measuredAt`, если время известно у всех; `receivedAt`, если неизвестно у всех;
`mixed`, если есть обе группы; `null`, если строк нет. Даже при `last` это
происхождение времени всех строк, а не только выбранного значения. Приём пакета
не подтверждает свежесть измерения.

Пустой интервал представлен точкой с `value/min/max=null`, нулевыми счётчиками
и `timeBasis=null`. В полностью пустом диапазоне возвращается та же сетка
интервалов, а не `points: []`. Интерполяции, подстановки нулей и переноса предыдущего
значения нет. React запрашивает выбранную метрику за 24 часа с `maxPoints=96`
или за 7/30 дней с `maxPoints=168` и показывает разрывы вместо соединения точек
через пустые интервалы.

Отсутствие обязательных полей и неверные значения дают 400 `VALIDATION_ERROR`
с `field=metric/from/to/maxPoints`; неверный порядок границ — `field=to`.
Неизвестные и повторяющиеся query-поля дают 400 `INVALID_QUERY` без `field`.
Примеры: [mean с пробелом](examples/measurements.series.mean.response.json),
[last](examples/measurements.series.last.response.json),
[полностью пустой ряд](examples/measurements.series.empty.response.json).

## Свежесть

`GET /assessments` возвращает `{astronautId, evaluatedAt, metrics, status, explanation, health}`.
`metrics` содержит шесть записей `{metric, quality, latestReceivedQuality}` в том же
порядке и с теми же правилами выбора, что `/measurements/latest`. Оба endpoint
используют одну чистую функцию domain. Отдельные HTTP-запросы могут увидеть разные
снимки БД и моменты оценки; карточка React использует качество из своего latest-ответа.

`quality` и `latestReceivedQuality` имеют одинаковую форму:

| Поле | Значение |
|---|---|
| status | missing, fresh, stale, unknownTime или clockSkew |
| measurementId | id оцениваемой записи, null только при missing |
| freshForSeconds | Окно свежести метрики в секундах |
| ageSeconds | Неотрицательный возраст с дробной частью для известного небудущего времени; иначе null |
| clockSkew | true только для status=clockSkew |

Окна заданы явно в `domain/metric_config.rs` и являются **демонстрационной политикой
сбора данных, не медицинскими нормами**:

| metric | freshForSeconds |
|---|---:|
| heartRate | 15 |
| systolicPressure | 3600 |
| diastolicPressure | 3600 |
| temperature | 3600 |
| sleepHours | 86400 |
| mood | 86400 |

| status | Условие |
|---|---|
| missing | Нет выбранной записи |
| unknownTime | Запись есть, measuredAt отсутствует |
| clockSkew | measuredAt позже evaluatedAt хотя бы на 1 ns |
| fresh | Известный небудущий возраст от нуля до окна включительно |
| stale | Возраст превышает окно хотя бы на 1 ns |

Будущее определяется сравнением разобранных моментов времени до вычитания.
Свежесть сравнивает точную длительность, а не усечённые целые секунды.
`ageSeconds` сериализуется числом после определения статуса; `receivedAt` никогда
не подставляется вместо неизвестного `measuredAt`. Доступность API и доставка
пакета не доказывают свежесть наблюдения. Исходные timestamps не переписываются.

Приём по-прежнему допускает `measuredAt <= now + 300 секунд`; ещё 1 ns отклоняется.
Этот допуск не делает будущее измерение свежим. После отката серверных часов ранее
сохранённая запись может оказаться более чем на пять минут в будущем: чтение вернёт
`clockSkew`, а не ошибку приёма. По мере продвижения часов качество пересчитывается.

Поля верхнего уровня `status` и `explanation` **deprecated**: они сохранены для
совместимости и описывают только одну самую поздно принятую запись
(`receivedAt` в UTC-миллисекундах DESC, затем id DESC). Для неё применяется окно
её метрики. Это не общий статус экипажа и не заключение о здоровье. Свежий пульс
может дать `not-evaluated` при устаревшем сне; новый интерфейс читает `metrics`.

| Legacy status | Качество выбранной записи |
|---|---|
| no-data | missing |
| unknown-time | unknownTime |
| clock-skew | clockSkew |
| stale | stale |
| not-evaluated | fresh; legacy-поле не содержит результатов правил |

Параметры query запрещены в обоих endpoint, включая неизвестные и повторяющиеся
имена: 400 `INVALID_QUERY`. Некорректный timestamp сохранённой записи даёт
500 `DATABASE_ERROR`. Демонстрационные правила BE-08 используют качество
каждой метрики, а не legacy summary.

## Объяснимая оценка BE-08

`health` вычисляется по тому же снимку измерений и времени, что `metrics`.
Содержит версию `be08-demo-1`, статус, количество оценённых показателей, правила,
пять образовательных карточек опасностей полёта и рекомендации по срочной помощи.
Подробные поля, пороги и источники: [be08-rules.md](be08-rules.md).

Каждое правило связано с конкретным measurementId и validUntil. `critical` имеет
приоритет над `attention`; отсутствие данных не скрывает сработавшее правило.
`noAlert` возможен только при полном покрытии пригодными результатами и означает
отсутствие срабатываний, а не здоровье. Неизвестное время, будущее время и устаревшие
записи не используются для текущего вывода. Без правила возвращается notEvaluated.

Клиент сверяет ID с latest, учитывает монотонно прошедшее время и соединение.
Оценка из кеша остаётся предыдущей, а не текущей; numeric thresholds на клиент
не копируются. Старый сервер без `health` поддерживается с явным состоянием
«правила недоступны». Лекарств, диагнозов и автоматической связи с врачом нет.

## Задачи

- `GET /tasks`: массив `{id, title, completedAt}`, сортировка по id по возрастанию.
- `PATCH /tasks/{id}`: только `{ "completed": true }` либо false.
- true устанавливает серверное UTC-время; false очищает его до null.
- Повтор true пока меняет completedAt. Идемпотентность по датам — BE-07.
- Неизвестная задача — 404 TASK_NOT_FOUND.
- `date` в JSON пока запрещён; `date` в query не выбирает день.

**Целевая семантика после BE-07:** день миссии в UTC; PATCH адресует конкретный день,
повтор выполнения сохраняет исходное время. Это ещё не контракт работающего API.

В BE-02 добавлена схема шаблонов и выполнения по UTC-дате. Существующий
недатированный API остаётся переходным интерфейсом; выбор дня через него ещё
недоступен. Подробности переноса старых отметок и ограничения миграции описаны
в [архитектуре](backend-architecture.md).

## Health

`GET /health` выполняет запрос к БД и возвращает:

```json
{ "status": "ok", "storage": "sqlite" }
```

Этот ответ подтверждает доступность API и SQLite, а не датчика или актуальность показателей.

## Единый формат ошибок

```json
{
  "type": "urn:space-health:error:validation-error",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invalid unit or value",
  "code": "VALIDATION_ERROR",
  "message": "Invalid unit or value",
  "field": "unit",
  "error": "Invalid unit or value"
}
```

`type` — стабильный URN с кодом в lowercase/kebab-case. `title` — стандартное
название HTTP-статуса. `detail`, `message`, `error` равны; `error` оставлен для
совместимости с прежними клиентами. Новая логика клиента использует `code` и
`field`, а не сравнивает текст. `field` может отсутствовать. Внутренние сообщения
SQLx, пути файлов и stack traces в ответ не включаются.

| HTTP | code | Когда |
|---|---|---|
| 400 | INVALID_JSON | JSON синтаксически неверен |
| 422 | INVALID_BODY | Неверный тип JSON-поля, отсутствующее/неизвестное поле или число вне i64 |
| 415 | UNSUPPORTED_MEDIA_TYPE | Нет подходящего JSON Content-Type |
| 413 | PAYLOAD_TOO_LARGE | Превышен лимит тела запроса |
| 400 | INVALID_QUERY | Не удалось декодировать query в ожидаемую структуру |
| 400 | INVALID_PATH | Некорректный параметр пути |
| 400 | VALIDATION_ERROR | Неверные metric/unit/value/time или параметры истории/series; отсутствующие обязательные параметры series |
| 400 | UNKNOWN_DEVICE | Устройство не зарегистрировано; field=deviceId |
| 409 | SEQUENCE_CONFLICT | Ключ сообщения занят другим содержимым |
| 404 | TASK_NOT_FOUND | Нет задачи с указанным id |
| 404 | NOT_FOUND | Нет указанного API-маршрута |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; заголовок Allow перечисляет допустимые |
| 500 | DATABASE_ERROR | Ошибка операции с БД или некорректный timestamp сохранённой записи |

Проверки могут остановиться на первой ошибке. Не полагаться на порядок нескольких
одновременных нарушений. Единый формат распространяется на API, но не на ошибки
раздачи статических файлов вне `/api`.

## Совместимость и развитие

Версия 0.8.0 добавляет `health` к оценке без изменения пути `/api/assessments`,
запросов, исходных quality или полей измерений. Потребители принимают это поле
опционально для работы со старыми BE-06 серверами. Новая реализация всегда
возвращает `health`; прежние JSON-примеры оставлены как fixtures совместимости.
Новая миграция не требуется. Отдельные правила версионируются независимо от API.

Версия 0.6.0 добавляет evaluatedAt и качество по метрикам в latest/assessments.
Старые поля latest и legacy status/explanation сохранены; status дополнен вариантом
`clock-skew` и использует окно метрики выбранной записи. Строгие клиентские схемы
необходимо обновить вместе с сервером. `/assessments` теперь отклоняет query.
Повреждённые сохранённые timestamps возвращают 500 DATABASE_ERROR вместо прежнего
400 INVALID_STORED_TIMESTAMP. Сырые измерения, история, series и формат ввода
не изменяются. Миграция БД не требуется.

Версия 0.5.0 — ревизия контракта, не новый URI-префикс. Пути `/api` сохранены.
По сравнению с 0.4.0 добавлен `/measurements/series`; формы существующих ответов
не изменены. Новая миграция не требуется. График React переходит с ограниченной
страницы raw history на целый семидневный ряд, сохраняя явные пробелы.

Версия 0.4.0 добавила историю и latest.
Переход с 0.3.0 требует обновления клиента: GET истории теперь возвращает envelope
вместо массива, фильтры действуют, неизвестные query-параметры отклоняются.
Заменить чтение массива на `response.items`, учитывать `hasMore`/`nextCursor`,
перенести обзор на `/measurements/latest`. Сервер и встроенный React-клиент
выпускаются вместе; старый массив параллельно не обслуживается. POST/PATCH
и формат ошибок не изменены. Миграция `0003` добавляет индексы, данные сохраняются.

В 0.3.0 по сравнению с 0.2.0 изменено сравнение повторов: эквивалентные моменты с разными
offsets теперь возвращают 200 вместо 409. Формы запросов, ответов и ошибок прежние;
изменение не требует новых полей клиента или миграции БД. Клиент не должен
полагаться на побайтовое сравнение `measuredAt` в повторном запросе и ответе.

В 0.2.0 по сравнению с 0.1.1 добавлено поле ответа `timeBasis`, история упорядочивается
по времени измерения с явным fallback, а оценка получила `unknown-time`.
Сервер и встроенный React-клиент обновляются вместе. Клиентам со строгими
схемами нужно добавить поле и вариант статуса; нельзя рассчитывать на прежний
порядок по времени приёма. Формы запросов POST/PATCH и ошибки BE-01 сохранены.
Клиент должен принимать `application/problem+json`, а также уметь показать
обычный текст ошибки от прокси.

Новые маршруты можно добавлять совместимо. Изменение массивов на envelope,
обязательных полей и дат задач требует обновления спецификации, примеров,
контрактных тестов и API-клиента в согласованном выпуске. Публичный период
поддержки/депрекации пока не объявлен: это локальный прототип без внешних клиентов.
