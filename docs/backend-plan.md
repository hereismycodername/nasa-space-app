# План разработки backend — Rust + SQLite

Статус: **BE-01–BE-04 выполнены**. BE-05–BE-12 остаются планом следующих изменений.
Текущая реализация описана в [контракте](contracts.md) и
[архитектуре модулей](backend-architecture.md).
Порядок определяется зависимостями и критериями готовности, без почасового расписания.

## 1. Цель и границы

Backend принимает ручные измерения и показания симулятора, сохраняет их,
предоставляет данные обзору и графикам, оценивает качество данных, возвращает
объяснимые демонстрационные предупреждения и управляет задачами дня миссии.

Архитектура первой версии:

```text
React / симулятор / будущий адаптер датчика
                    ↓ HTTP JSON
              Axum: маршруты и DTO
                    ↓
       Сервисы измерений, правил и задач
                    ↓
            SQLx → локальная SQLite
```

Один Rust-процесс также раздаёт production-сборку React. Для работы нужен доступ
к локальному серверу; внешнее интернет-соединение не требуется после подготовки
зависимостей и сборки. Обязательный стенд — ноутбук; Raspberry Pi проверяется
отдельно на реальном устройстве.

В первой версии один демонстрационный астронавт. UI-фокус: пульс, температура,
сон и самочувствие; существующую поддержку давления в API сохраняем.
Не добавляем в этот этап облачную синхронизацию, аккаунты, LLM, MQTT/WebSocket,
распознавание изображений или прошивки нескольких плат.

## 2. Что уже сделано

Проверено по текущему исходному коду:

- Cargo workspace, Axum, Tokio, SQLx, SQLite, миграции при запуске.
- POST /api/measurements с проверкой структуры, единиц и части границ ввода.
- Привязка deviceId к astronautId и source на сервере.
- Уникальность сообщения по deviceId + sessionId + sequence.
- Повтор возвращает существующую запись; изменение содержимого с тем же ключом — 409.
  Время при повторе сравнивается по моменту UTC с точностью парсера до наносекунды.
- Вставка и чтение измерения выполняются транзакционно; конкурентные повторы
  используют уникальный ключ БД и не перезаписывают исходную запись.
- История: фильтры metric/from/to/limit, envelope items/hasMore, лимит 100 (максимум 500);
  сортировка по числовому времени измерения с fallback на приём и явным timeBasis.
- Latest: шесть метрик независимо, известное время и последняя запись без времени раздельно.
- Оценка свежести только по одной последней принятой записи, общий порог 15 секунд;
  неизвестное время измерения даёт unknown-time.
- Одна постоянная задача без даты миссии; повтор completed=true обновляет её timestamp.
- Миграция 0002 добавляет шаблоны и выполнения задач по UTC-дате; старый API
  остаётся переходным до BE-07, записи синхронизируются транзакционно.
- Проверка БД через /api/health, раздача dist, корректное завершение по Ctrl+C.
- Симулятор пульса с повторами при недоступности сервера.
- Интеграционные тесты и smoke со сверкой сохранности после перезапуска.

Основные пробелы: series и агрегация данных для графиков,
свежесть каждой метрики и clockSkew, публичные задачи по датам,
демонстрационные правила и сценарии демоданных.

## 3. Ответственность двух backend-разработчиков

| Разработчик | Ответственность | Владеет решениями |
|---|---|---|
| Ты — Backend 1 / техлид | HTTP API, контракты, валидация, качество данных, правила, логика задач | Поведение API и интеграция с React |
| iwbhappy — Backend 2 | SQLite, миграции, запросы истории, симулятор, сборка и запуск | Схема хранения и эксплуатация локального стенда |

Разработчик пишет тесты своей логики; QA проверяет сценарии независимо.
Участник продукта поставляет объяснения, источники и спецификации правил.

Целевая структура после разбиения текущего lib.rs:

```text
server/src/
  main.rs                    # iwbhappy: запуск, конфигурация, завершение
  lib.rs                     # ты: сборка Router и состояния приложения
  api/                       # ты: handlers, DTO, query-параметры, ошибки
  domain/
    measurements.rs          # ты: валидация и правила приёма
    freshness.rs             # ты: качество и свежесть данных
    assessments.rs           # ты: демонстрационные правила
    tasks.rs                 # ты: семантика ежедневных задач
  storage/                   # iwbhappy: SQLite-запросы и транзакции
server/migrations/           # iwbhappy
server/tests/                # каждый — тесты своей функции
simulator/                   # iwbhappy
scripts/                     # iwbhappy: запуск, подготовка демо, smoke
```

В BE-01 созданы api/, domain/ и storage/. Отдельный freshness.rs появится при
BE-06; текущая совместимая оценка находится в domain/assessments.rs.
Не вводим универсальные repository-фреймворки, event bus или микросервисы.

## 4. Порядок реализации

| Этап | Задачи | Условие перехода |
|---|---|---|
| Основа | BE-01, BE-02 | Зафиксированы DTO, границы модулей и семантика времени |
| Данные и действия | BE-03, BE-04, BE-05, BE-07 | Надёжный приём, история, последние значения и задачи доступны через API |
| Оценка и сценарии | BE-06, BE-08, BE-09 | Свежесть, объяснения и воспроизводимые наборы данных согласованы |
| Интеграция и выпуск | BE-10, BE-11 | React работает с настоящим API, проверки проходят, сборка воспроизводится |
| Подключение железа | BE-12 | Предыдущая версия принята; выбраны конкретные плата и датчик |

Этапы не требуют последовательной работы всей команды. После согласования
контрактов ты работаешь над API и domain, iwbhappy — над хранением и симулятором.
Frontend получает JSON-примеры сразу, QA проверяет каждый готовый сценарий.

### BE-02 — Уточнить модель данных и времени — выполнено

**Владелец:** iwbhappy. **Согласует семантику:** ты. **Зависимость:** BE-01.

- Сохранить таблицы устройств и измерений и уникальный ключ сообщений.
- Зафиксировать measuredAt как время измерения, receivedAt как время первого приёма.
- Добавить сравнимое числовое UTC-время для фильтрации и сортировки;
  не сравнивать RFC3339-строки с разными offsets как обычный текст.
- Для записи без measuredAt оставить время измерения неизвестным.
- Для отображения истории допустим fallback на receivedAt, но ответ должен
  явно обозначать timeBasis=receivedAt. Это не доказательство свежести измерения.
- Добавить таблицы шаблонов задач и выполнения по дате миссии.
- Новая схема вводится новой миграцией; существующую 0001 не переписывать.
- Перенести имеющиеся задачи и отметки без удаления исходных измерений.
- Дату старого выполнения выводить из сохранённого completedAt в UTC;
  если восстановить её нельзя, явно зафиксировать ограничение миграции,
  а не приписывать выполнение текущему дню.

**Готово:** миграция работает на пустой и заполненной БД; единый момент времени
с разными часовыми поясами корректно фильтруется и сортируется.

Граница BE-02: сравнимое время и диапазоны проверяются на уровне хранения.
Публичные фильтры `from/to` относятся к BE-04. Таблицы ежедневных задач подготовлены,
но выбор даты в API остаётся BE-07. Подробности переноса и его ограничений —
в [архитектуре](backend-architecture.md).

### BE-03 — Завершить надёжный приём измерений — выполнено

**Владелец:** ты; SQL и транзакции — iwbhappy. **Зависимости:** BE-01, BE-02.

- Использовать существующий POST /measurements.
- Проверять metric/unit, конечность числа, допустимый ввод и корректность времени.
- Не позволять клиенту назначать source, astronautId, id или receivedAt.
- Сохранить результаты: 201 новая запись, 200 повтор, 409 изменённое сообщение.
- Зафиксировать сравнение timestamp при повторе: нормализовать время до
  сравнения, чтобы одинаковый момент с другим offset не становился конфликтом.
- При повторе сохранять первоначальные id и receivedAt.
- Поздно пришедшую запись сохранять в истории, но не считать новым измерением
  только потому, что она только что получена.
- Обеспечить одну запись при одновременных одинаковых запросах.
- Гарантировать, что ошибка БД не приводит к ответу об успешном сохранении.

**Готово:** тесты покрывают повтор, конфликт, параллельные повторы, неизвестное
устройство, неверные единицы, timestamp и попытку передать серверные поля.

Валидация ввода не является медицинской оценкой; клинические пороги здесь не вводим.

Реализованная точность сравнения — первые девять цифр дробной секунды Chrono,
а не миллисекундные поля сортировки. Исходные строки и первый `receivedAt`
сохраняются. Контракт и ограничения повторной доставки описаны в
[contracts.md](contracts.md), устройство транзакции — в [архитектуре](backend-architecture.md).

### BE-04 — Последние значения и история — выполнено

**Владелец:** iwbhappy; handlers/DTO подключает ты. **Зависимость:** BE-02.

- Добавить GET /measurements/latest: отдельное последнее значение для каждой метрики.
- latestKnownMeasurement определять по `measured_at_ms DESC, id DESC` среди записей
  с известным временем измерения; время получения на выбор не влияет.
- Если последнее полученное сообщение не имеет measuredAt, вернуть его отдельно
  от latestKnownMeasurement. Неизвестное время не должно скрывать последнее
  измерение, время которого достоверно указано; frontend различает эти поля.
- Возвращать явное отсутствие записи для метрики, по которой нет данных.
- Добавить фильтры metric, from, to, limit к GET /measurements.
- Диапазон [from, to) — по эффективному времени UTC в миллисекундах; limit 1…500, по умолчанию 100.
- История возвращает envelope items/hasMore через выборку limit + 1; React-клиент обновлён.
- Добавить индексы под выборку конкретного астронавта, метрики и времени.

**Готово:** частый пульс не вытесняет сон из обзора; запоздавший старый пакет не
перекрывает более новое известное измерение; фильтры не смешивают метрики.

### BE-05 — Данные для графиков

**Владелец:** iwbhappy. **Зависимость:** BE-04.

- Добавить GET /measurements/series с metric/from/to и ограничением числа точек.
- Для длинного периода агрегировать поток по UTC-интервалам.
- Для непрерывных метрик документировать выбранную агрегацию, например mean
  вместе с min/max/count; сырые данные не изменять.
- Для ежедневных и дискретных показателей использовать согласованную семантику,
  например последнее значение интервала; не усреднять шкалы молча.
- Возвращать единицу, интервал, способ агрегации и timeBasis.
- Не заполнять пробелы выдуманными измерениями; явно обозначать отсутствие данных.

**Готово:** семидневный график охватывает запрошенный диапазон, имеет ограниченный
размер ответа и совпадает с расчётами на известном тестовом наборе.

### BE-06 — Качество и свежесть данных

**Владелец:** ты. **Зависимости:** BE-02, BE-04.

- Вычислять статус отдельно для каждой метрики: missing, fresh, stale, unknownTime.
- Вынести сроки свежести в явную конфигурацию показателей.
- Различать потоковый пульс и ежедневные сон/самочувствие.
- Отсутствие measuredAt не заменять утверждением, что измерение свежее.
- Согласовать допустимое рассогласование часов: сейчас приём разрешает timestamp
  до пяти минут в будущем. Такая запись получает признак clockSkew и не считается
  безусловно свежей; тесты покрывают границу допуска и время за её пределами.
- Различать доступность API, факт приёма данных и время самого измерения.
- Передавать текущий момент в функции расчёта, чтобы тесты не зависели от ожидания.
- Результат сделать общим для обзора и оценки правил.

**Готово:** свежий пульс не обновляет статус сна; задержанный пакет не выглядит
свежим; пустая БД и неизвестное время представлены самостоятельными состояниями.

### BE-07 — Ежедневные задачи

**Владелец:** ты; schema/queries — iwbhappy. **Зависимость:** BE-02.

- Разделить шаблон задачи и выполнение для astronautId + taskId + missionDate.
- Для прототипа использовать дату UTC и явно отдать её frontend.
- GET /tasks?date=YYYY-MM-DD: дата по умолчанию — текущая дата миссии на сервере.
- PATCH /tasks/{id}: явно передавать дату и completed, чтобы переход через

- Шаблоны и сохранённые выполнения объединять при чтении; фоновый планировщик
  для наступления нового дня не требуется.

**Готово:** дни независимы, история сохраняется после перезапуска, повтор PATCH
не меняет уже подтверждённое время, отмена снимает отметку только указанной даты.

### BE-08 — Объяснимые демонстрационные правила

**Владелец:** ты. **Зависимости:** BE-06 и спецификации участника продукта.

- Реализовать до двух правил чистыми функциями отдельно от HTTP и SQL.
- Вход: измерения, качество данных, параметры правила и момент оценки.
- Для отсутствующих, устаревших или неизвестных по времени данных возвращать
  insufficientData, а не заключение о нормальном состоянии.
- Результат: ruleId, ruleVersion, status, explanation, measurementIds,
  suggestedAction, sourceUrls, demonstrationOnly.
- Статусы правил отделить от статусов свежести: notEvaluated, insufficientData,
  noAlert, attention. noAlert означает только отсутствие срабатывания этого правила.
- Сохранять в коде или версионированном контенте пороги, тексты и ссылки,
  а не в случайных строках HTTP-handler.
- Обновить GET /assessments: качество данных и список результатов правил.
- Для воспроизводимости возвращать evaluatedAt и используемую версию правил.

**Готово:** QA воспроизводит срабатывание/несрабатывание на фиксированных входах;
каждое предупреждение связано с конкретными измерениями. Непроверенные числовые
пороги явно демонстрационные. Диагнозы и назначения не генерируются.

## 6. Целевая схема БД

| Сущность | Назначение | Важные ограничения |
|---|---|---|
| devices | deviceId → astronautId + source | Устройство известно до приёма данных |
| measurements | Сырые значения, единицы, source, время измерения/приёма | UNIQUE(device_id, session_id, sequence) |
| task_templates | Название, инструкция, идентификатор задачи | Стабильный ID шаблона |
| task_completions | Выполнение по астронавту, задаче и дате | UNIQUE(astronaut_id, task_id, mission_date) |

Свежесть и предупреждения сначала вычисляются при запросе. Отдельное хранение
истории оценок не нужно для первой версии; возвращаемые версии правил и IDs
измерений позволяют объяснить текущий результат. Сырые измерения не заменять
агрегатами графика.

## 7. Целевые API для согласования

| Метод и маршрут | Назначение | Состояние |
|---|---|---|
| GET /api/health | Доступность сервера и БД | Уже есть |
| POST /api/measurements | Приём одного измерения | Есть, дорабатывается |
| GET /api/measurements | Фильтрованная история | Есть без фильтров, дорабатывается |
| GET /api/measurements/latest | Последнее значение каждой метрики | Новый |
| GET /api/measurements/series | Ограниченный ряд для графика | Новый |
| GET /api/assessments | Качество данных и результаты правил | Есть заглушка свежести, меняется DTO |
| GET /api/tasks?date=… | Задачи даты миссии | Есть без дат, дорабатывается |
| PATCH /api/tasks/{id} | Выполнение задачи указанной даты | Есть без дат, меняется DTO |

Отдельный публичный endpoint для сброса БД не создаём. Подготовка демо — локальная
команда, которая работает с отдельным файлом.

## 8. Зависимости и параллельная работа

```text
BE-01 → BE-02 → BE-03 ─────────────────────→ BE-09
             ├→ BE-04 → BE-05
             │        └→ BE-06 → BE-08 ───→ BE-09
             └→ BE-07

Готовые функции + React → BE-10 → BE-11 → BE-12 (железо)
```

BE-08 также ждёт спецификаций от участника продукта. Подготовка baseline-демо
в BE-09 не должна ждать реализации правил. QA начинает с существующего API,
а не после завершения BE-10.

Для каждого Issue: один владелец, разрешённые модули, зависимости, пример запроса,
критерии приёмки и проверки. Один PR — одна законченная функция или рефакторинг.
Миграции и Cargo-зависимости меняет iwbhappy; контракт согласует техлид с потребителем.
Другой backend-разработчик проверяет PR; два обязательных ревью не требуются.

## 9. Проверки и критерии готовности backend

Обязательные автоматические сценарии:

- Повтор и параллельный повтор — одна запись; конфликт — 409 без перезаписи.
- Ошибочный ввод и неизвестное устройство не изменяют БД.
- Фильтры, лимиты и сортировка времени корректны при разных offsets.
- Поздняя старая запись остаётся в истории, но не подменяет более новую.
- Latest выдаёт метрики независимо от частоты их поступления.
- График ограничен по размеру и сохраняет смысл агрегации и пропусков.
- Свежесть отдельная для каждой метрики; unknownTime не превращается в fresh.
- Правила не оценивают недостаточные данные как нормальное здоровье.
- Задачи независимы по датам, повтор выполнения не меняет completedAt.
- Миграция заполненной БД и перезапуск сохраняют подтверждённые данные.

Команды проверки:

```bash
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
npm run check
npm run test:smoke
```

Backend готов к сдаче, когда React работает с реальным API, обязательные сценарии
приняты QA, API-документация соответствует сборке, демо воспроизводится командой,
release запускается без внешнего интернета, а ограничения явно записаны.

Завершённые задачи помечаются явно. Остальные пункты не описывают уже работающие
функции и выполняются отдельно по указанным зависимостям.
