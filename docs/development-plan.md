# План разработки на один день: 2 frontend + 2 backend + QA + продукт

План рассчитан на 12 рабочих часов от старта командной разработки, включая
интеграцию и подготовку показа. Последние 3 часа — исправления и сдача.
Текущее окружение уже создано; повторно его не разрабатываем.

## 1. Результат дня

Один астронавт в одной демонстрационной миссии может:

1. Увидеть показания симулятора, источник и время каждого измерения.
2. Ввести показатель вручную и увидеть его в истории.
3. Просмотреть динамику за 7 дней.
4. Открыть объяснение предупреждения с причиной, следующим действием и источником.
5. Выполнить задачу на текущий день миссии.
6. Продолжать работать без интернета при доступном локальном Rust-сервере.
7. Перезапустить сервер без потери истории и отметок задач.

Обязательные показатели UI: пульс, температура, длительность сна, самочувствие.
Давление уже предусмотрено контрактом, но его UI — дополнительная задача.
Пульс поступает из симулятора; остальные показатели вводятся вручную и входят
в синтетическую историю. Все демонстрационные данные явно обозначаются.

Не включаем в обязательный объём: аккаунты, облачную синхронизацию, LLM,
распознавание изображений, 3D-анатомию, подключение нескольких типов плат,
установку PWA, реальные клинические назначения.
Raspberry Pi — дополнительная проверка, если устройство уже есть и готово.
Ноутбук с локальным сервером — обязательная демонстрационная площадка.

## 2. Роли

| Роль | Человек | Главная ответственность |
|---|---|---|
| Backend 1 / техлид | Ты | API, правила, контракты, интеграция |
| Backend 2 / инфраструктура | iwbhappy | SQLite, история, симулятор, запуск |
| Frontend 1 | Asterisksy-zxc | Обзор, графики, общие UI-компоненты |
| Frontend 2 | Участник 4 | Ввод, задачи, взаимодействие с API |
| QA | Участник 5 | Приёмка, регрессия, воспроизводимые баги |
| Продукт / научное содержание / демо | Участник 6 | Сценарий, источники, тексты, презентация и сдача |

Техлид — дополнительная ответственность Backend 1, а не седьмая роль.
iwbhappy принимает инфраструктурные решения и подменяет интегратора при необходимости.

## 3. Первый совместный час

- [ ] Каждый запускает проект по README; проблемы окружения выявляются сразу.
- [ ] Выбираем один компьютер для показа, проверяем production-сборку.
- [ ] Создаём GitHub Issues из задач ниже и назначаем по одному владельцу.
- [ ] Фиксируем API и примеры ответов в `docs/contracts.md`.
- [ ] Согласуем четыре показателя, единицы, шкалу самочувствия и статусы.
- [ ] Выбираем UTC как время миссии для этого прототипа; дата задач берётся
      с сервера, UI явно показывает дату миссии. Это проектное упрощение.
- [ ] Frontend 1 делает минимальный набор компонентов и каркас навигации.
- [ ] Backend 1 разделяет текущий `server/src/lib.rs` на модули, чтобы два
      разработчика не редактировали один файл одновременно.
- [ ] QA заводит матрицу проверок; участник 6 — сценарий показа и реестр источников.

## 4. Frontend 1 — Asterisksy-zxc

**Область:** `src/features/dashboard/`, `src/shared/ui/`, `src/index.css`,
`src/App.tsx`. Общие стили и каркас приложения меняет один владелец.

### FE1-1. Каркас и общие компоненты — до часа 2

- Навигация: обзор, ввод, задачи.
- Компоненты карточки, кнопки, поля, индикатора состояния, пустого состояния.
- Согласованные размеры, типографика и статусы; смысл передаётся текстом,
  а не только цветом.
- Frontend 2 подключает свои экраны через согласованные экспорты.

**Готово:** все экраны доступны, компоненты можно использовать без изменения CSS.

### FE1-2. Обзор и история — до часа 4

- Последнее значение каждого из четырёх показателей, единица, источник и время.
- График выбранного показателя за 7 дней, правильный порядок времени.
- Состояния: загрузка, нет измерений, ошибка API, устаревший показатель.
- При потере API сохранять график как последние полученные данные с явной пометкой.

**Зависимости:** BE2-1 (фильтры истории), BE1-1 (контракт); до готовности использовать
один общий JSON-пример ответа, который не выдаётся за рабочую интеграцию.

**Готово:** новая запись появляется без перезагрузки страницы; единицы не смешиваются;
обновление пульса не меняет свежесть сна.

### FE1-3. Объяснение предупреждений — часы 4–7

- Карточка с причиной, связанными измерениями, следующим действием и источником.
- Разделять отсутствие/устаревание данных и демонстрационное предупреждение.
- Не показывать «здоров» при отсутствии реализованных правил.
- Проверить экран на ноутбуке и ширине 390 px.

**Зависимости:** BE1-3 и P-2. **Готово:** QA может проследить предупреждение до
конкретных данных, правила и источника/пометки демонстрационного правила.

## 5. Frontend 2 — ввод и задачи

**Область:** `src/features/check-in/`, `src/features/tasks/`, `src/data/`.
Этот участник — единственный редактор общих API-клиентов и клиентских типов
после согласования контракта с Backend 1.

### FE2-1. API-клиент и формы — до часа 4

- Использовать существующий POST /measurements.
- Форма выбора показателя и ввода значения; одна запись за одно сохранение.
- Проверять обязательность, число, единицы и согласованные границы ввода.
- Показать состояния отправки, успеха и ошибки; не терять введённое при ошибке.
- Блокировать повторный клик, повтор запроса сохраняет тот же sessionId/sequence.
- После успеха сбрасывать идентификатор отправки для следующего измерения.
- Включить источник manual и серверное время в отображение результата.

**Готово:** корректное значение попадает в SQLite и обзор; ошибочное не создаёт
запись; повтор после сетевого сбоя не порождает дубликат.

### FE2-2. Ежедневные задачи — часы 4–7

- Список задач на дату миссии, отметка и отмена выполнения.
- Показывать состояние сохранения и ошибку; UI не должен сообщать об успехе
  до подтверждения API либо обязан откатить оптимистическое изменение.
- Показывать актуальную дату миссии и инструкцию для каждой задачи.

**Зависимость:** BE1-2. **Готово:** состояние сохраняется после перезагрузки,
выполнение вчерашней задачи не завершает сегодняшнюю.

### FE2-3. Интеграция и исправления — часы 7–9

- Проверить переход «ввод → сохранение → обзор» вместе с Frontend 1.
- Проверить клавиатуру, подписи полей, отображение ошибок на мобильной ширине.
- Устранить баги QA в своей области.

## 6. Backend 1 — ты

**Область после разделения:** маршруты, DTO, `server/src/api/`,
`server/src/domain/`, подключение модулей в `server/src/lib.rs`.

### BE1-1. Контракты и границы — первый час

- Согласовать DTO, коды ошибок и общие примеры с обоими frontend-разработчиками.
- Сохранить существующие правила идентичного повтора и конфликта sequence.
- Разделить HTTP, правила и доступ к БД. Не менять существующие пути без необходимости.
- Взять на себя интеграционные решения; не блокировать каждое изменение двумя ревью.

### BE1-2. Ежедневные задачи — до часа 4

- Согласовать с BE2 миграцию шаблонов задач и выполнений по дате миссии.
- Реализовать получение задач текущей даты и изменение конкретного выполнения.
- Вычислять дату и completedAt на сервере; явный контракт дня миссии.
- Проверить новый день, отмену, повтор запроса, неизвестную задачу.

**Готово:** задачи разных дней независимы и не теряются при перезапуске.

### BE1-3. Объяснимые правила — часы 4–7

- Отдельно вычислять свежесть каждого показателя: потоковый пульс и ежедневный
  сон имеют разные сроки актуальности. Не применять 15 секунд ко всем метрикам.
- Реализовать максимум 2 демонстрационных правила по спецификации участника 6.
- Ответ содержит ruleId, статус, причину, measurementIds, следующее действие,
  ссылки и признак demonstrationOnly.
- Если обоснование не готово, оставить правило демонстрационным и явно маркировать.
- Тесты границ правила, недостатка и устаревания данных.

**Готово:** результат воспроизводим по входным данным; отсутствие данных не
превращается в заключение о здоровье; UI получает готовое объяснение.

### BE1-4. Интеграция — короткими окнами весь день

- Объединять небольшие PR по готовности, не накапливать всё до вечера.
- Контрольный сквозной прогон в часы 4, 7, 9.
- После часа 9 принимать только исправления и решения по сдаче.

## 7. Backend 2 — iwbhappy

**Область:** `server/src/storage/`, `server/migrations/`, `server/src/main.rs`,
`simulator/`, `scripts/`, `.github/`, конфигурация запуска.

### BE2-1. Хранилище и история — до часа 4

- Фильтры metric/from/to/limit; согласовать сортировку, ограничение и примеры.
- Отдельно обеспечить последние значения по каждому показателю (например,
  `GET /measurements/latest`). Общий лимит 500 записей потока пульса не должен
  вытеснять последнюю запись сна из карточек обзора.
- Для 7-дневного графика использовать ограниченный объём/агрегацию, а не
  бесконтрольную выдачу всего двухсекундного потока.
- Поддержать схему ежедневных задач для BE1 отдельной миграцией.
- Проверить чтение, сохранность, миграции с существующей БД и дедупликацию.

**Готово:** фронт получает историю выбранного показателя за нужный период,
старые данные сохраняются после миграции.

### BE2-2. Демоданные и симулятор — часы 4–7

- Детерминированная синтетическая история четырёх показателей за 7 дней.
- Три сценария: обычные данные, условие демонстрационного предупреждения,
  прекращение поступления показаний.
- Подготовить отдельную demo-БД; команда восстановления работает только с ней.
- Не удалять пользовательскую БД для сброса показа. Для нового показа можно
  создавать новый файл из подготовленного seed и передавать DATABASE_URL.
- Сохранить повторы сообщений с тем же идентификатором при временном отказе API.

**Готово:** любой член команды воспроизводит сценарии одной документированной
командой; источники данных явно синтетические.

### BE2-3. Сборка и запуск — часы 7–9

- Проверить release-бинарник + dist на демонстрационном компьютере.
- Проверить доступ с другого устройства в доверенной локальной сети.
- Зафиксировать точные команды запуска, остановки и восстановления демо.
- Если Pi уже доступна: ограничить первичную попытку запуска 45 минутами;
  при блокере продолжать демо на ноутбуке, а проблему Pi записать отдельно.

**Готово:** показ запускается без Vite и без внешнего интернета; симулятор
может идти отдельным процессом. Не заявлять поддержку платы без испытания.

## 8. QA — отдельный участник

**Область:** `docs/qa-checklist.md`, браузерные сценарии, воспроизводимые Issues,
результаты приёмки. Разработчики пишут тесты своего кода сами.

### QA-1. Подготовка — часы 0–2

- Запустить проект по README на другом компьютере.
- Составить матрицу критериев ниже и подготовить набор корректных/некорректных данных.
- Согласовать приоритеты: P0 — блокирует запуск, потеря/искажение данных;
  P1 — ломает обязательный сценарий; P2 — косметика/дополнительная функция.

### QA-2. Приёмка по мере поступления — часы 2–9

| Сценарий | Ожидаемый результат |
|---|---|
| Пустая БД | Понятное «нет данных», без ложного благополучия |
| Симулятор работает | Показания и график обновляются, источник виден |
| Ручной ввод | Новая запись в БД и обзоре с правильными единицами |
| Неверное значение/единица | Ошибка, данные не записаны |
| Двойной клик/повтор запроса | Одна запись |
| Тот же sequence, другое тело | Конфликт, исходная запись не изменена |
| Симулятор остановлен | Пульс становится устаревшим |
| Пульс свежий, сон старый | Сон остаётся устаревшим |
| API остановлен | Явная потеря связи, сохранение не выдаётся за успешное |
| API восстановлен | Опрос и передача восстанавливаются |
| Сервер перезапущен | История и задачи сохранены |
| Новый день миссии | Новые выполнения задач, вчерашние не переносятся |
| Интернет отключён, LAN сохранена | Локальное приложение работает |
| Предупреждение | Причина, связанные данные и маркировка правила видны |
| Production-сборка | Основной сценарий работает без Vite |

Баг: commit/сборка, шаги, ожидаемое, фактическое, серьёзность, screenshot/log.
Один Issue — одна воспроизводимая проблема. Проверка относится к конкретной
сборке: после новых изменений повторяется затронутый сценарий.

### QA-3. Финальная проверка — часы 9–11

- Прогнать обязательный сценарий на production-сборке и мобильной ширине.
- Подтвердить отсутствие открытых P0/P1 либо согласовать исключение функции.
- Записать commit SHA готовой версии и известные ограничения.
- Повторить короткий smoke после последнего исправления.

**Результат:** проверенная версия и понятный список фактических ограничений.

## 9. Шестой участник — продукт, научное содержание и демо

Это полноценная роль с результатами с первого часа, а не только презентация вечером.

### P-1. Сценарий и границы MVP — первый час

- Описать один путь астронавта: обзор → проверка → измерение → объяснение → действие.
- Для каждого экрана дать короткие тексты и критерии понятности.
- Зафиксировать обязательные функции; новые идеи складывать в backlog.
- Проверить актуальные требования, дедлайн и формат сдачи своего мероприятия.

### P-2. Источники и спецификация правил — часы 1–4

- Использовать ресурсы challenge и NASA; вести URL, название, что источник
  подтверждает и чего он не подтверждает.
- Описать назначение каждого показателя простыми словами.
- Для двух выбранных правил подготовить входные данные, условие, текст причины,
  следующий шаг, пример срабатывания и пример несрабатывания.
- Разделять научный контекст и числовой порог: общая статья о рисках не подтверждает
  клиническую норму. Непроверенные пороги маркировать как демонстрационные.
- Проверить, что тексты не обещают диагностику/назначение лечения.

**Передача:** BE1 получает спецификацию правил, FE1/FE2 — тексты, QA — примеры.

### P-3. Демонстрация — часы 4–9

- Согласовать с BE2 три воспроизводимых набора данных.
- Подготовить 3-минутный показ: проблема, живой поток, ручной ввод, объяснение,
  локальная автономность, следующий шаг развития.
- Подготовить слайды: задача, пользовательский путь, архитектура, реальное
  применение ресурсов NASA, ограничения и дальнейшее развитие.
- Проверить соответствие рассказа действительно работающему продукту.

### P-4. Сдача — часы 9–12

- Репетиция с командой, запись резервного видео работающей сборки.
- Собрать материалы и ссылки согласно требованиям мероприятия.
- Проверить доступность ссылок и комплектность перед отправкой.
- Ответственный за финальную отправку — ты; участник 6 готовит всё к ней.

**Результат:** проверяемая связь с задачей NASA, понятные тексты и готовый показ.
Если у участника сильные технические навыки, он также может писать контентные
JSON-fixtures, но не должен становиться незапланированным третьим backend-разработчиком.

## 11. GitHub и Claude Code

- Один Issue = один владелец, ограниченная задача и критерий готовности.
- Один PR = проверяемый кусок работы, а не весь модуль за день.
- Ветка: `feature/<issue>-<short-name>`; main должен оставаться запускаемым.
- Frontend-разработчики проверяют друг друга; backend-разработчики — друг друга.
  Для обычного PR достаточно одного назначенного ревьюера.
- Изменения контрактов согласуются с Backend 1 и потребителем до реализации.
- Миграции и Cargo-зависимости ведёт BE2; frontend-зависимости — FE1.
- QA проверяет функциональность; его участие не заменяет техническое ревью.
- Общий чат — блокеры и решения; детали задачи — в Issue/PR.
- Обновление каждые 60–90 минут: готово / следующий результат / блокер.
  Блокер дольше 15 минут сообщается сразу с воспроизведением.
- Claude Code не считается автоматически читающим все обсуждения. Человек
  передаёт согласованные изменения своему агенту и отвечает за результат.
- Не публиковать изменения, не отправлять комментарии и не создавать внешние
  действия от имени участника без его поручения соответствующему агенту.
